# 产品演进方向

本页描述 Mizar 的长期产品方向与需要持续维护的边界，**不跟踪具体 Issue 的进度、发布清单或日期**。当前已交付能力见[产品介绍](guide/product.md)，稳定版本与变更记录见 [GitHub Releases](https://github.com/Starfie1d1272/Mizar/releases)，实际开发安排见 [GitHub Issues](https://github.com/Starfie1d1272/Mizar/issues) 和 [Milestones](https://github.com/Starfie1d1272/Mizar/milestones)。

## 长期产品原则

- **比赛事实优先**：正式 Program 的比分、地图、名单、时间与目标状态来自可验证的数据源；展示层不复制权威状态，不凭效果需要编造事件。
- **基础路径独立**：常规 CS2 观战、GSI、HUD、雷达和 OBS 播出不应依赖可选插件、外部赛事平台或实验数据源才能运行。
- **渐进增强**：高级运镜、赛事资料、历史统计、音乐、视觉包和观察辅助均应可选；缺失或故障时明确降级，不能干扰正在进行的直播。
- **自动编排、人工接管**：自动操作必须遵守现场制作人员意图，可中断、可恢复，不重放过期操作。
- **发布可追溯**：源代码、构建产物、版本身份与验收证据一致；升级与卸载保留用户数据，操作可诊断、失败可恢复。

产品与技术职责分别由[产品说明](guide/product.md)、[架构](reference/architecture.md)、[数据源能力](guide/data-source-capabilities.md)和[发布规范](development/release-readiness.md)维护，不在路线图重复详细规则。

## 产品演进主线

### 1.x — 完善日常制播

优先解决真实比赛中遇到的正确性、可靠性和操作问题，并持续改善分发、安装与更新体验。逐步提升 BP、HUD、节目动画、音乐、赛事资料与低频数据插页的可读性和表现力；按明确消费者需求推进可分享视觉资源及第三方适配。

**原则**：小缺陷可以独立发布补丁，功能增强按兼容性发布次版本；不为凑版本号将无关需求捆绑发布，也不以长周期重构阻塞必要修复。

### 2.x — 高级观战控制与事件驱动制播

从自动包装既有比赛画面，进一步扩展到游戏内摄像机控制、电影式开场镜头与有证据支持的精确事件表现。优先评估 MulNX 等已有工具作为**可选 Provider**，通过受控接口与 Mizar 的节目编排协作，而不是在 Mizar 中复制镜头轨道引擎。

2.0 的收尾范围包含高级运镜、节目音乐和第一版私有观察辅助。私有辅助通过一路较早时间轴接收击杀事件，与延迟节目对齐，在工作台显示槽位、昵称和倒计时；开关与时间设置独立于游戏启动方式。具体入口见[操作手册](guide/quick-start.md#游戏与观战)。纳入版本范围不代表真实赛事验收已完成。

正式节目精确事件增强（[#215](https://github.com/Starfie1d1272/Mizar/issues/215)）仍未完成产品接入闭环。连接弹窗中的节目源用于真实 CS2；提前提示不等于两路无头接收或精确命中等正式节目效果已经交付。普通 GSI、HUD、雷达及公开输出继续使用节目时间轴。

第三方 API、兼容性、赛事许可、人工接管与失败回退仍需按候选实测。高级控制不可替代常规 Program 数据源；不能由外部工具或未经验证的事件直接驱动正式赛果。

### 后续观察辅助与精确事件

在首版私有提示上，继续研究更可靠的时间轴对齐、断流恢复和经过验证的事件扩展。较早时间轴信息始终与公开 Program、HUD、OBS 和网站 LIVE 严格隔离；不可用时正常播出不受影响。

正式节目事件需要独立证明来源、比赛身份、地图执行、时序与新鲜度，并验证重复、迟到和重连行为。双路无头接收及同账号端点共存须先验证，不能从私有提示推定这些能力已可用。后续范围由真实需求和证据决定，不再将已进入 2.0 的首版私有提示整体列为 3.x 研究。

## 从方向到交付

以上主线表达产品演进目标，**不是功能保证、日期或固定版本清单**；具体发布版本仍应遵守[兼容性与发布规则](development/release-readiness.md)。

- 产品方向和技术不变量由本页与相应 reference/design 文档维护；只有方向或决策改变才修改。
- 调研结论、用户反馈、实施范围、优先级与进度在 **Issue / PR** 维护；无需将每次新增、关闭或改期同步成文档改动。
- **GitHub Milestone** 只用于范围已明确、准备实际交付的版本；更远期的候选保持未排期，不设置虚假的截止日期。
- 每个正式版本的已交付事实、变更和必要升级说明写入 **Release Notes**，而不是在路线图回填完成状态。
