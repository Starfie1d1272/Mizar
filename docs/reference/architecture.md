# 系统架构

本文维护当前职责与依赖规则；产品价值见[产品定位](../guide/product.md)，接口和输入解释分别见[协议](protocol.md)、[游戏数据语义](telemetry.md)。决策理由保存在 [ADR](../decisions/README.md)。

## 数据与控制

```text
本地比赛资料 / RivalHub      CS2 GSI / 可选事件源
           ↓                       ↓
        赛事适配器              遥测适配器
           └────────→ Core ←───────┘
                  运行状态、身份、连续性
                          ↓
                  各消费面的独立投影
                  ├─ 播出画面与雷达
                  ├─ 制作控制与诊断
                  └─ 私有观察辅助

Companion 组装运行时、持久化和接口
  ├─ 节目编排 → 场景控制 → OBS
  ├─ 公开投影 → 外部数据输出
  └─ Web / Windows 桌面 → 制作人员
```

赛事平台拥有官方赛事资料与结果，Mizar 拥有本地实时观测。独立模式与连接模式共享运行时，仅赛事资料来源不同。Mizar 不直连 RivalHub 内部数据库；DAK 等赛后证据不进入低延迟播出主循环。

本机赛事的BO3默认禁选规则保存在既有LocalTournamentStore赛事资产中，供未录入BP的比赛继承；本场草稿使用规则编译出同一MatchDocument的veto/maps事实，已有事实优先恢复，赛事默认变更不改旧BP。本场规则调整不顺带修改赛事默认，在线补录不改平台身份或网站数据。缺省旧配置保留既有流程，见[ADR-0040](https://github.com/Starfie1d1272/Mizar/blob/3b187e168ad755ede595eb8371bfaf5933c044fa/docs/decisions/0040-event-bo3-authoring-rules.md)。

## 模块职责

应用内更新由 Companion 持有已认证版本、检查偏好及下载状态；桌面宿主通过本次运行的私有能力核对安装计划，正常退出后启动资源目录外的恢复工具。浏览器不能提供可执行路径或调用安装命令，更新不成为比赛或制作状态的第二来源。元数据、信任根与恢复契约见[应用内更新](updates.md)。

官方示例素材由 Companion 的[单一资源 Store](../../apps/companion/src/resource-store/README.md)持有独立持久缓存和状态。安装器复用同一 Store；来源授权与清单消费复用资源契约模块，缓存启动离线复验证据及实际文件。原资源 URL 从活动版本读取；无活动缓存时保留 Full 随包来源，错误不混合版本。激活与制作生命周期及更新共用互斥保护，现场只准备素材。

资源管理目录只汇总资源 Store 和 MulNX 工具的状态，不另存安装或当前版本。MulNX 镜头内容仍属于发行版，目录仅展示来源名称；工具检查沿用既有控制入口。

安装器的素材准备入口必须成功打开 Store；初始化失败时，启动错误通过 `cause` 保留原始异常，由安装器既有脱敏日志出口记录错误码和系统调用等细节。普通 Companion 启动仍允许回退 Full 随包素材，不改变其容错行为。

## 比赛与赛事上下文

`MatchContext` 与 `MatchDocumentV1` 以单场比赛为根，`competition` 和 `stage` 可以为空。两方名称、赛制、地图及 BP 引用属于比赛；赛事名称和赛程窗口是可选组织信息。空名单表示未提供名单，不能阻止文档导入、本地保存或节目投影；游戏观察身份仍由既有遥测归一化负责。

来源适配器保留 opaque 参赛方标识，不将它解释成赛事报名 ID。赛事比赛继续使用已有标识与行为；无赛事比赛不创建占位赛事，也不进入赛事赛程。现有赛事授权的在线输出需要真实赛事上下文；无赛事本地制作不会伪造授权并回传。

已配对的当前赛事比赛由 Companion 定期刷新；正在加载的手动选择优先，后台刷新不能使其失效。兼容的同场资料自动激活；地图计划更新复用运行时的未执行判定。本地 BP 冲突时保留地图和禁选、刷新名单与解说，并保留网站候选供明确确认。关联比赛、资料来源与推送资格分别展示；不通过本地覆盖获取在线授权。见 [ADR-0049](https://github.com/Starfie1d1272/Mizar/blob/3b187e168ad755ede595eb8371bfaf5933c044fa/docs/decisions/0049-connected-match-refresh-and-diagnostic-retention.md)。

本地比赛回收站与比赛列表由同一 LocalTournamentStore 原子持久化。移入回收站同时清理赛事赛程和旧选择引用，最终写盘前再次检查 MatchContext 当前引用；现场和隐藏工作区的当前比赛禁止删除。准备状态和等待画面下，未接收游戏数据且未启动游戏的新选择可明确确认解除；已有游戏接收证据或重启恢复的选择，需要 Host 实际完成游戏收尾并确认全机 CS2 已退出，通过私有运行时令牌确认当前比赛与上下文修订。该资格仅在内存保存，绑定、制作修订和游戏接收游标变化后失效，重启需重新确认；不以数据过期或浏览器自报推断游戏关闭。回收最后一场并解除选择使用制作生命周期的同一互斥，最终写盘守卫也检查此资格。回收保留完整比赛文档和原赛程位置，不移除共享队伍与赛事资产。恢复保留比赛身份、名单、地图、BP 与结果，赛事展示资料采用现有赛事最新值，恢复不激活比赛或修改当前运行进度。

## 单一事实与独立投影

`SeriesProgress` 只拥有已知地图及观测胜场，不把上游总比分塞回地图计数器。比赛文档的终局结论独立保留 `recorded / pending / omitted`：已结束时节目投影使用上游确认的总比分；待补或不提交结果仍是已结束，比分为空。该投影规则同时供系列摘要和具备身份映射的队伍比分使用，不补造地图。进行中的上游汇总比分不覆盖实时观测胜场。

Core 只维护一份 `RuntimeState`，通过 `ProgramProjection`、`RadarFrame`、`OperatorProjection`、`ObserverAssistProjection` 和 `DebugProjection` 提供不同视图。

- 渲染层只消费自己需要的投影，不重新解释生死、名单、伤害统计或游戏时钟。 Web 的 `ProgramView` 接收 HUD、节目场景或 BP 展示输入；实时订阅和雷达通道适配留在宿主，导演进度由场景状态传入。
- 诊断可以看到更多信息，但不成为正式节目的数据源。
- 选手稳定身份使用 Steam64，阵营与参赛方身份分开。名单和统计算法由[遥测语义](telemetry.md#名单与伤害统计)统一说明。
- 展示配置故障不改变比赛数据；展示摘要也不向领域状态回写。

## 系列赛进展与恢复

`SeriesProgress` 由 Core 定义、Companion 的唯一运行时组合持有，消费 `RuntimeTransition`、比赛资料与已证明的阵营映射。它维护可选计划与实际执行的绑定、有限回合历史、已冻结地图结果和系列比分。创建时冻结 sourcePlan 的 planned / awaiting_plan / unplanned 模式、允许图池和指纹；已有地图为 planned，无地图的赛事比赛为 awaiting_plan，无地图的独立比赛为 unplanned。awaiting_plan 不接受 GSI 自动建图，BP 形成后可在没有执行事实的准备状态平滑切换 planned；指纹来自上游计划，不从可变观测记录重新计算。明确为 unplanned 时，图池内的真实地图可以按观测顺序追加 mapId 为空、selection 未知的本地记录；不创建上游 canonical 地图。只有上一图已经完成、实际地图尚未使用且未达系列胜场或图数上限时才追加下一图，缺少阵营证明时保留观测但不确认胜者。已有计划仍要求严格匹配，错图或缺失上一图结果不能自动跳过。

尚未绑定任何地图执行、回合或赛果的准备状态允许更新地图计划；首次建立时可使用比赛资料中的已完成结果；明确只有人员差异且完整当前双方账号、阵营与计划地图均已证明时，可记录观察到的单图结束并接续相邻计划图，但保持正式比分、胜者为空且不增加系列胜场，由结果待核对诊断说明；运行后普通资料刷新不能覆盖本地已冻结赛果。来自网站绑定或其有效缓存、具有完整比分和完成时间的同图结果属于明确上游完成证据：比赛、参赛方、赛制及冻结计划兼容、前序图已完成且本地比分未知时，可补入该结果以恢复相邻图接续；保留实际执行与原回合历史，不补造遥测结束事件，不改名单或回写网站。网站结果与本地比分、已知回合胜者数量或未进行状态冲突时保留本地事实并显示核对网站赛果提示。后续推进来自运行时转换、系列赛归约器与明确人工证据。实际地图与计划不符时保留局内数据，系列绑定进入 `needs_operator`，等待确认。

比赛、参赛方、赛制和有序地图计划兼容时，普通资料刷新更新系列展示中的队名与队标，并由既有检查点保存；不替换地图执行绑定、回合历史或已捕获选手摘要；未知比分仅按上述明确完成证据补入。地图比分与完成时间不属于计划变化；实际 BP、选边、地图或参赛方变化仍走原确认门禁。身份或计划冲突时保留原展示身份与系列事实，不能把新参赛方资料套在已运行系列上。

回合结束转换是回合历史的首要来源；`map_round_wins` 仅恢复缺失、补充未知胜因或校验，不覆盖已冻结获胜方。冲突保留原事实、标记 `partial` 并报告诊断。

同一地图结束观测中的可证明绝对回合历史在地图结果冻结前完成归约，涵盖没有独立回合结束转换的最后一回合；这不允许后续输入改写已完成地图。

恢复检查点使用 v2，有大小上限，按比赛、参赛方、赛制和冻结 sourcePlan（包括图池）核对兼容性，仅在业务边界原子写盘。空计划、空观测是合法初始状态；后续追加观测不会改变计划指纹，刷新和重启保留这些记录。旧检查点不迁移，按既有不兼容诊断处理。兼容检查点加载后同样核对网站明确完成证据，避免旧的未知结果遮住新赛果；本地冻结结果优先，冲突显式保留。恢复后还要与当前回合、比分和回合历史核对，结构与执行兼容性分别核对。关闭服务先停止生产者，再等待已提交检查点写完。

## 连续性与事件

| 标识或类型                      | 表达                             |
| ------------------------------- | -------------------------------- |
| `liveSessionId`                 | 比赛与生产会话的绑定             |
| `producerInstanceId`            | 一次本地服务运行                 |
| `mapEpoch`                      | 地图的一次实际执行               |
| `sourceGeneration` / 数据源序号 | 单个数据源的连接与读取连续性     |
| 高频快照                        | 当前状态，可被更新覆盖           |
| `RuntimeTransition`             | 已观测到的状态边界               |
| `OperatorCommand`               | 有明确结果的人工操作             |
| `ReliableObservation`           | 转换发生时的上下文派生的可靠观测 |
| `Incident`                      | 运行问题与诊断                   |

这些概念不能合并成全局序号或万能事件。数据源重连只使依赖它的证明失效；可选事件源或 Lookahead 重连不自行推进正式节目的地图执行编号。投递、去重和背压由[协议](protocol.md#本地实时通道)维护。

Core 在地图执行中保留一个“曾观测正式阶段”的连续性证明，不把它作为当前阶段。只有同图重新出现完整的热身、回合零、双方零分且没有冲突的非空历史时，才推进执行编号，并通过既有转换清除未完成地图的历史、单图统计和目标计时。CS2 热身可以省略历史字段，零回合与零比分的完整热身仍提供执行重开的证据；地图关键字段缺失、降级、普通回合回退和重连本身不证明重开。已冻结完成地图不因该转换被撤销。决定见 [ADR-0037](https://github.com/Starfie1d1272/Mizar/blob/3b187e168ad755ede595eb8371bfaf5933c044fa/docs/decisions/0037-witnessed-same-map-restart.md) 与其条件修订 [ADR-0038](https://github.com/Starfie1d1272/Mizar/blob/3b187e168ad755ede595eb8371bfaf5933c044fa/docs/decisions/0038-warmup-without-round-history.md)。

## 正式节目与观察辅助隔离

新鲜正式输入允许手动选择 Gameplay，包括未绑定赛事的 demo；这只接管画面，不建立赛事归属或官方身份。Core 的 Gameplay 展示投影在地图未绑定或身份不符时使用中立身份，制作控制保留后台选择与系列事实。手动摘要展示不确认赛果，自动编排仍受严格绑定与阶段门槛约束，见 [ADR-0032](https://github.com/Starfie1d1272/Mizar/blob/3b187e168ad755ede595eb8371bfaf5933c044fa/docs/decisions/0032-manual-summary-and-demo-presentation.md)。

正式节目消费观战客户端的 GSI；精确事件是可选增强。Lookahead 使用独立的较早时间轴，只能形成私有辅助信息。

桌面包携带固定版本的观察器 external-node 组件，解析器复用同包 Companion 的 Node。构建时核对发行 ZIP、组件清单及文件摘要；版本、来源提交和入口由[组件配置](../../apps/companion/src/telemetry/observer-component.json)维护。源码与许可随组件保存。

打开工作台保留按当前偏好启动或接入 CS2 的一键流程，不要求 GoTV 地址，不自动重连历史地址。每张图由用户在工作台显式确认该图地址与密码后，才提交节目连接和独立早源意图；输入草稿、保存偏好和窗口呈现不提交连接。MulNX 自动控制资格来自当前受管或借用实例的进程身份及网关归属，不能只由启动偏好推断；HUD 原值在真实控制操作前保存，退出仍通过既有事务恢复。换图的新地址更新两路，停止旧早源并清空旧提示与时间对齐；工作台、OBS 与游戏继续运行。同地址早源重试复用配置修订、租约和已接受的节目命令，不能将旧地址重试视为换图完成。

Companion 启动观察器前在已验证的 state 下逐级创建并核对 `data/observer` 父目录，拒绝非目录、符号链接和不可写路径；独立 UUID 末级目录仍由组件 driver 非递归创建；每次重试使用同一已验证父目录下的新末级，不依赖前次建目录成功。每次尝试保留编号、次数、终止阶段、退出码／信号、进程启动原生码、就绪与超时／取消、stdout 协议结果及报告分类；只接收允许列表原因与原生码，不保存子进程原始 stderr、密码或任意路径。在有界 stderr 缓冲中从后向前选择最后一份通过固定 schema 校验的终止报告，尾随文本不覆盖报告；找不到报告时再对明确的 pre-report token 单独归因，组件未暴露的细分阶段保持未知。诊断订阅者异常分别隔离，不阻断子进程清理或重连。既有会话日志记录各次尝试，私有状态另保留最多八次有观察器会话关联的摘要；再次启动清空当前故障，历史保持独立。支持包直接包含结构化观察器状态及保留期内日志，日志轮转与缺口沿用既有契约。

工作台通过 Host 确认当前已启动或明确借用的 CS2 实例，再提交私有观察器连接意图。Host 依据该实例的安装位置选择 Steam API 和当前 host 版本，Companion 串行管理启动、停止与来源切换；每次新连接推进来源代际，已有私有消费者沿用同一订阅入口。连接信息通过 stdin 交给组件，输出目录位于用户运行数据目录。

观察器使用独立的 Windows Job，句柄由当前 Desktop 持有。启动中继先加入该 Job，再建立本次尝试的嵌套 Job 并启动 Python，解析器继承进程归属。正常停止使用 stdin EOF 等待组件收尾；中继或 Desktop 异常退出由 Windows 回收对应子树。Host 每两秒依据持有的游戏句柄续约，Companion 在六秒租约过期后停止观察器。结束工作台先完成观察器停止，再继续游戏收尾。Companion 的既有异常恢复策略继续负责其余制播状态。

- Lookahead 不能作为正式节目备用源；任一链路故障不改变另一链路的角色。
- 未来字段不能先进入公开数据，再依靠 CSS、窗口或 OBS 裁剪隐藏。
- 安全边界由投影、类型和协议结构保证，窗口捕获策略是额外防线。
- 制作工作区、控制栏和本机 HUD 覆盖允许远程捕获；正式 OBS 输出使用独立的游戏捕获与播出 Browser Source，不依赖制作窗口的捕获排除。策略理由见 [ADR-0022](https://github.com/Starfie1d1272/Mizar/blob/3b187e168ad755ede595eb8371bfaf5933c044fa/docs/decisions/0022-remote-workspace-capture.md)。
- 本机 HUD 仅在受管游戏或现场工作区、控制栏位于前台时显示；准备中心、核对弹窗等其他窗口位于前台时隐藏，避免遮挡操作。
- 同一地图执行的普通重连、暂停与恢复保留已有早源事件和延迟估计；不同比赛或地图执行仍隔离。
- 私有提示在可靠校准前等待，不使用固定延迟估计。提前源 cursor 的回合时钟与节目 GSI 原始倒计时按地图、原始回合计数和连续 live 段匹配；短间隔正常推进时插值到相同剩余时间，用进程内单调接收时刻差形成样本。至少三个样本跨五秒且偏差稳定才更新中位估计，同时到达的成批记录和明显速率跳变不能当作独立推进；契约没有批次标识，按实时速率释放的上游积压无法排除。冻结结束事件单独接纳，以接收时刻作为辅助边界；未经验证的事件 tick 不是精确时间。炸弹、拆弹、暂停、断点与未知状态不跨段插值；暂停累计 tick 的含义未验证，暂停或累计值未知时不测量；累计值非零时，下一回合仅在规则开始时间与冻结结束提交 tick 接近且累计值稳定时采样，不推测暂停补偿。已知提前源新比赛或正式期后明确归零热身时隔离时钟，等待节目地图执行切换；两路 world 并非共同执行 ID，缺少边界证据时不能排除同名同回合重启歧义。死亡变化只撤下唯一可归属的已发生提示和提供诊断，不再参与校准。短时缺证保持估计，断流或停滞引起连续性丢失后暂停提示直到新证据恢复；比赛或同图新执行边界清空；提前源先换图时，等待节目切换并保留有界的新图事件；临时不新鲜保留缓冲。已显示提示固定截止时刻，未显示事件允许按新估计调整。事件按其接收时刻调度；源内部或进程管道积压可能使事件接收时刻与 cursor 接收时刻的偏差不同，时钟估计不保证精确事件时刻。

接入能力见[数据源矩阵](../guide/data-source-capabilities.md)，尚未交付的研究见 [RFC](https://github.com/Starfie1d1272/Mizar/blob/3b187e168ad755ede595eb8371bfaf5933c044fa/docs/rfcs/0001-lookahead-observer.md)。

C4 资源的解压、解析、预测索引与计算由 Companion 的单个 Worker 承担，最多保留两张地图和十个在途预测。Core 继续校验当前数据资格；结果按地图、数据源代际、地图执行和完整预测输入匹配，只触发当前状态重新投影。同一投影的十人预测合并为一次 Worker 消息，整批写入精确输入缓存后通知刷新。普通实战帧的等待发布最多合并十六毫秒，既有完整快照保留原游标；未变化的不可用项（例如已阵亡选手）不阻止其余选手的等待合并，新出现的不可用原因立即发布。完成时重投影最新状态，超时公开等待，不把旧估算拼接到新帧。新鲜度、代际、地图、身份、回合或比分边界立即发布。见 [ADR-0029](https://github.com/Starfie1d1272/Mizar/blob/3b187e168ad755ede595eb8371bfaf5933c044fa/docs/decisions/0029-c4-worker-isolation.md)与 [ADR-0035](https://github.com/Starfie1d1272/Mizar/blob/3b187e168ad755ede595eb8371bfaf5933c044fa/docs/decisions/0035-bounded-c4-publish-coalescing.md)。

## 雷达与展示配置

雷达领域完成世界坐标到地图坐标的转换；共享展示包负责插值、平滑、跳变重置和自动聚焦动画。外部网站消费已经校准的公共坐标，不复制地图校准。[包说明](../../packages/radar-view/README.md)维护集成方法。

共享雷达展示缓存底图滤镜、烟雾纹理、火焰模糊及 C4 着色，缓存按表面大小、样式和地图边界失效，有界保留，不改变地图校准与插值。火焰模糊按亚像素栅格精度复用近似纹理，避免自动缩放的连续浮点值让每帧重建缓存；精度由[缓存实现](../../packages/radar-view/src/render-cache.ts)维护。烟雾生命周期容忍一 tick 的寿命回跳，明显回退或位置断裂仍重建；同生命周期已知阵营不因死亡后的 owner 变化而丢失。

HUD 配置独立于比赛数据：组件内容、布局、外观和比赛投影分别拥有自己的职责。描述符维护组件方案、设置和尺寸，编辑器与播出使用同一解析结果和渲染器。Companion 持久化配置，浏览器缓存不是权威来源。保存、启用、版本校验与文件交换规则见[协议](protocol.md#hud-配置)。

设计变量 → 基础组件 → 组合组件 → 功能页面的规则由[设计系统](../design/README.md)维护。

## 制作生命周期与节目编排

Companion 拥有 `preparation / live / hidden` 制作生命周期；它们不等同于比赛或 OBS 状态。进入现场需要比赛资料；结束制作通过场景控制器核实 OBS 等待画面、再释放平台数据源，失败保留现场状态供重试，不删除本地比赛。人工重新选择当前场景仍核实 OBS；退出使用独立的安全收尾意图。OBS 切场失败时仅在本次原生进程检测明确证明 OBS 未运行后完成本地等待状态，适用于从未启动 OBS 以及制作人员已关闭 OBS 的恢复；断线、鉴权失败或检测未知本身不能证明输出已停止。OBS 仍运行时保留安全切场要求，提示连接后重试，或人工确认停止输出并关闭 OBS 后重试，不自动停止输出或关闭用户启动的 OBS。结束意图先停用自动运镜；安全收尾成功后 Host 才关闭受管 CS2 并恢复设置，恢复失败保留原恢复事务与重试入口。

标准 Steam 与 MulNX 均在启动前准备同一受管配置事务。MulNX 提交启动前持久记录待确认状态，核对唯一新游戏进程、所选程序路径和游戏网关所属 PID 后才绑定该事务；待确认期间后台恢复不能自行认领游戏。启动器首次窗口使用隐藏启动参数。退出受管 MulNX 先持有本次注入的卸载事件并提交一次停止，再等待信号并核对同一游戏进程中的模块已消失；入队或断线不是完成证明。确认结果持久绑定进程身份，游戏正常关闭失败后重试先复核模块仍不存在，再继续关闭与恢复，不重复提交停止。事件或模块检查失败保留游戏与事务。用户自行启动的游戏仍按借用语义处理。

MulNX 启动超时后，状态的 `mulnxLaunchResumable` 表示同一 Host 仍持有本次已提交请求的启动器句柄；`launch_mulnx` 的 `resumeOnly` 只核对该请求，记录不存在或未提交时返回 `result: not-found`，不会启动新游戏。调用时仍须重新验证实例。满足条件时可重试原进入意图，只核对已提交请求对应的启动器和唯一游戏实例、网关与受管事务，清理启动参数后接续，不再次发送启动请求。卸载已提交但信号或落盘未确认时，重试只核对同一存活实例中的模块是否消失，确认后继续收尾，不再次发送停止命令。借用游戏结束工作台后，Host 保留本次停止操作的只读进程句柄，以便确认迟到的卸载；不会再次发送停止命令。Host 重启后不凭旧启动器 PID 认领游戏。

MulNX 启动记录尚未清理时，受管事务对外显示启动结果待确认；恢复入口要求用户确认已取消启动并关闭游戏与启动器，Host 再核查进程与目标后恢复，不以普通恢复请求的返回值代替完成证明。

Host 持有已验证进程身份的句柄发送正常关闭请求，分别保留窗口枚举失败、关闭消息拒绝、无可关闭窗口、等待超时与等待失败的原因。消息发送成功不证明游戏已退出，权限拒绝也不能放宽身份或配置恢复检查；本机诊断记录阶段、API、错误码与受管 PID／创建时间，并随既有退出事件进入诊断包。失败时由使用者在游戏内正常退出后重试，不自动强杀或关闭不归属进程。

本地 Demo 试播在同一制作生命周期内使用临时比赛资料及独立运行会话，不新增运行时或 Demo 管理库。Host 持有原生文件选择能力和播放请求；Companion 在启动前持久记录试播隔离，暂停正式检查点读写、资料修改、采集及在线输出，真实 GSI 仍经过原生产解析与投影。服务重启发现未完成记录时先隔离输入，不自动恢复正式绑定。试播保持手动编排；进程运行、收到有效观战数据和加载选定 Demo 是不同事实。

结束试播先隔离在途 GSI 并确认 OBS 等待画面，Host 只按既有进程身份关闭受管游戏并恢复配置，成功后才确认完成隔离事务；失败保留恢复记录供重试。完成后恢复正式资料、清空试播遥测、统计、计时和提示，推进会话与数据源代际；在明确重新进入正式制作前继续拒绝 GSI，避免迟到的 Demo 输入污染正式检查点。用户显式启用的 HUD 配置保留。

MulNX 已启动的外部游戏可显式进入同一试播生命周期。试播记录只增加外部游戏所有权标记；Host 仍按 PID、创建时间与所选安装路径借用查询句柄，绑定本次试播 ID 的原生运镜租约。临时比赛、正式检查点与在线输出沿用原隔离，仅开放连接、手动运镜试播、接管、跳过和断开。结束时先断开运镜，再完成试播资料恢复并释放句柄，保留外部游戏和配置。服务重启按持久所有权标记恢复隔离；外部试播完成不要求关闭游戏，也不产生受管停机证明。受管恢复记录与外部标记同时存在时保留隔离并拒绝混合收尾。

桌面和 Web 的进入现场入口先读取当前 OBS 连接与场景检查结果；未通过时打开连接引导，不提交制作命令。此准备门禁不复制生命周期状态，也不改变现场运行后的离线恢复能力；理由见 [ADR-0023](https://github.com/Starfie1d1272/Mizar/blob/3b187e168ad755ede595eb8371bfaf5933c044fa/docs/decisions/0023-workspace-preflight-and-density.md)。

CS2 的自动发现、手动安装选择和 GSI 配置目录统一由 Host 管理。按 Steam AppID 730 清单定位，验证程序与新版 cfg，按安装根目录去重；保存的手动位置同时供 GSI 与启动使用。显式 GSI 修复仅重建当前安装记录绑定的 Mizar 文件，先保留修复前文件与记录，沿用原令牌与首次恢复备份，原子替换配置并更新指纹；自动准备不覆盖人工修改，身份或备份不完整时保留现场并报错。修复归档独立于安装恢复目录，恢复不删除修复前文件。文件冲突、重复发送与读取失败分别展示，支持包只导出有限问题码、数量和阶段；见 [ADR-0047](https://github.com/Starfie1d1272/Mizar/blob/3b187e168ad755ede595eb8371bfaf5933c044fa/docs/decisions/0047-shared-cs2-installation-discovery.md)。

桌面通过准备检查后，由 Host 启动或复用本次受管理 CS2，再提交进入现场。启动发现要求唯一 Steam 进程、可读取且存在的程序位置，以及有效的当前账号整数；Host 通过持有的原生进程句柄读取映像路径与创建时间，不依赖 PowerShell 的模块路径，安装目录候选不能替代运行进程身份。发现期间及提交 Steam 启动请求前复核唯一进程的 PID、创建时间、程序路径和当前账号，变化或读取失败时拒绝提交；缺失、格式异常或越界账号明确报告账号不可用，不猜测 userdata 目录。注册表的有符号 DWORD 仍按原 32 位账号恢复，底层读取异常保留在本机诊断。 配置接管前先在本机保存视频与机器帧率文件的原始字节；机器帧率文件确实不存在时记录缺失而不构造文件，正常接管仍拒绝、保留模式可继续，存在但不可读仍报错；`fps_max` 原值可为有限非负小数，恢复保留原始文本。重复视频字段分别诊断同值与冲突，嵌套与格式错误单独报告，不自动取第一或最后值。备份成功且接管失败未留下待恢复事务时，可明确选择「保持原游戏设置继续」：仍由 Host 跟踪 Steam 请求及进程身份，但不应用自动画质、帧率、游戏窗口布局或本机 HUD 覆盖，结束后只清理启动记录，保留现场备份且不覆盖游戏的新设置。备份失败、未完成事务及进程归属不明仍阻止危险操作。结束制作成功后正常关闭该游戏并恢复临时视频与帧率配置；隐藏现场不关闭。配置文件与进程身份、备份及重启恢复只由 Host 管理，网页发送固定意图。画质与帧率使用独立的有限选项，默认最高画质与 60 帧／秒；启动脚本中直接设置的帧率纳入同一恢复事务，避免覆盖本次上限。细节见 [ADR-0026](https://github.com/Starfie1d1272/Mizar/blob/3b187e168ad755ede595eb8371bfaf5933c044fa/docs/decisions/0026-managed-cs2-launch-and-restoration.md)及其局部替代 [ADR-0045](https://github.com/Starfie1d1272/Mizar/blob/3b187e168ad755ede595eb8371bfaf5933c044fa/docs/decisions/0045-managed-game-quality-and-frame-budget.md)。

现场核对使用独立 `tool-review` WebView，路由 `/workspace/review`，复用现有只读投影、名单差异和同步健康判断。Host 将核对窗口放在工作台所在显示器中心，并主动请求前台焦点；它是赛前流程和异常提醒的明确例外，不改变普通面板操作的焦点规则。网页面板通过受限的 `open_tool` 类型打开窗口；核对窗口只能通过专属能力关闭自身，不接受任意窗口标签。关闭或隐藏工作台会销毁核对窗口。正常状态不会触发网站写入；恢复自动与热身选择仍使用原有带 revision 的控制命令。核对窗口的「复制隐藏命令并返回游戏」复用 Host 显式焦点意图守卫，要求调用窗口仍为前台且游戏会话仍匹配；复制成功不表示命令执行。赛前完成标记仅是当前本地会话与核对依据的 UI 确认，跨窗口同步不承担比赛或网站状态权威。

现场工作台由独立 CS2 与两块桌面面板组成。每个受管 CS2 进程首次进入现场时，仅在准备中心仍为前台的情况下尝试一次聚焦游戏；首入在后台最多等待渲染窗口三十秒，期间前台切走或游戏退出即取消；窗口就绪后只尝试一次聚焦，超时或失败不后台重试。底栏的「返回游戏」是新的显式聚焦意图，Host 校验调用面板仍为前台、工作台可用以及受管进程身份后才尝试；执行时已切换面板或应用、隐藏或退出会使请求失效。普通面板操作、节目「比赛中／BP」切换和「恢复布局」不申请游戏焦点，重新显示面板也不主动选择输入目标。Host 在既有有界窗口巡检中检测从其他应用切回成员，只为本次受管理进程恢复最小化的同组窗口并调整普通 Z 序，保留用户选中的输入焦点；联动不重排布局、不修改缩放或置顶状态、不嵌入游戏，也不操作外部启动的游戏。进程身份沿用 ManagedCs2 的 PID、创建时间与程序路径验证，操作期间持有原进程句柄；显式借用的外部实例仅允许用户点击“返回游戏”时验证身份并聚焦，不参加自动首入聚焦、布局或窗口组联动。游戏最小化不释放既有窗口目标。隐藏、退出、成员失效、模态窗口和前台再次切走会取消联动；异步恢复只提交一次，并以单调时钟观察最多两秒，不在后台反复抢焦点；API 失败或超时按本次事务在既有 DesktopLog 中记录一次阶段、API、错误码和受管 PID／创建时间，不记录路径，正常取消不记故障。Alt-Tab 与任务栏仍由 Windows 展示各顶层窗口，置顶或独占全屏游戏不参与自动联动；原生效果与 CS2／OBS 捕获仍须实机验证。

现场窗口采用窗口级全屏 Shell 标记，让任务栏在现场处于活动状态时退到其后，不修改系统自动隐藏设置；隐藏、退出或更换游戏窗口撤销标记。标记成功后按完整显示器边界排布，失败沿用工作区。受管理 CS2 使用无边框窗口，启动参数与临时视频配置都使用既有工作台布局算出的游戏尺寸，保持 75% 上限与 16:9 客户区，左栏贴屏幕底部，与游戏、底栏连续平铺；游戏拒绝无边框时保留原生外框避让。外框缩放成功不代替客户区对齐；游戏拒绝运行中的分辨率变更时不再次缩小无边框外框，本机覆盖保持隐藏并提示重新进入工作台。DPI 与窗口变化共用同一 Host 物理布局；现场 WebView 自身的缩放变化也通过既有工作线程合并重排，不依赖游戏窗口同时改变尺寸或 DPI，隐藏期间的变化在恢复现场时处理。决策及异常退出边界见 [ADR-0030](https://github.com/Starfie1d1272/Mizar/blob/3b187e168ad755ede595eb8371bfaf5933c044fa/docs/decisions/0030-workspace-fullscreen-shell.md)、[ADR-0031](https://github.com/Starfie1d1272/Mizar/blob/3b187e168ad755ede595eb8371bfaf5933c044fa/docs/decisions/0031-borderless-workspace-game.md)与[ADR-0036](https://github.com/Starfie1d1272/Mizar/blob/3b187e168ad755ede595eb8371bfaf5933c044fa/docs/decisions/0036-workspace-sized-cs2-launch.md)。

`ProgramDirector` 消费既有投影与 BP，通过唯一 `ProgramSceneController` 请求 OBS 切场。现场默认自动，手动操作保持到显式恢复。自动切场最多一个在途请求、不离线排队；切换前后检查上下文、代际、版本与时限。失败停止自动推进。具体节目顺序与时长来源见[节目规范](../design/program-direction-v1.md)。

`MusicDirector` 独立消费同一节目投影、制作生命周期与实际 Take 的 started 边界，不把画面 hold 或 Director 的 blocked 当成音乐控制权。背景音乐互斥，开场音效独立叠加；不建立比赛事实的第二来源。比赛、参赛方、地图顺序及执行编号组成音频实例键，暂停实例跨标签变化保持，来源重连不建立新实例。当前游标、已消费事件、人工停止和随机安装身份以本机原子状态保存，过期请求在每个 OBS 副作用前取消。普通淡化由轮询推进，不延迟紧急停音或画面切换。

OBS 音乐适配通过持久连接核对媒体状态；仅操作随机安装名和已登记 UUID 同时一致的 `ffmpeg_source`，不按可碰撞的展示名接管来源，不改游戏声、麦克风、全局设备或其他集合。BGM 与 Stinger 连接到 Mizar 的节目场景，禁止激活重启和离开场景关闭。OBS 自主播放器在控制断连时无法保证立即停音，重连先核对再纠正，异常向现场提供可操作提示。本地音乐库复用资源模块的安全目录与原子写入基础能力；音乐 ZIP 是独立的不受信任本地格式，不经过或冒充官方资源身份／签名。私有契约见[节目音乐](music.md)。

`BpSession` 只维护播放状态；正式 BP 由比赛投影派生。本地补录不改写在线比赛身份，演示来源只在 BP 内存会话生效。命令与来源切换见[协议](protocol.md#bp-播放与补录)。

`ProgramPresentationStore` 在地图结束时冻结已确认比分并捕获选手摘要，最多保留五图。相同生产实例、会话、来源代际和地图执行的后续新鲜 gameover 观测，只有阵营名单完全一致且比分不变时，才允许已观察到的 K/A/D 收敛；缺失字段不擦除已捕获值，不回写比分或回合历史。换执行、来源、比赛、断流或身份不符后保留已捕获摘要，跨图保留、换比赛清除。静态画面的进入资格与已播连续性分开，不恢复旧游戏时钟；见 [ADR-0039](https://github.com/Starfie1d1272/Mizar/blob/3b187e168ad755ede595eb8371bfaf5933c044fa/docs/decisions/0039-terminal-player-summary-settlement.md)。

Companion 的 OBS 模块持有唯一输出控制状态，通过持续的 Outputs 订阅和重连快照观察直播、录像与外部手动操作；快照不能覆盖读取期间的新事件，旧连接回调不能写入新代际。人工开始／停止使用明确请求，不依赖本地切换布尔值。每类输出的在途保护跨窗口生效，并与配置修改和修复互斥；请求回执与实际完成分别判断，超时后核实状态，不自动重放命令。网页只消费本机输出视图和提交有限意图，桌面、Core 与自动节目编排不持有输出控制权。

OBS 由 Companion 检查和修复，只管理 Mizar 自有场景。连接后的自动准备可在输出停止时创建或切换到 Mizar 集合，补齐场景并准备默认音频，其他集合保留；已有自定义音频或游戏、窗口捕获附带的音频只检查，不重复采集。页面共享自动准备请求进度并合并并发请求，准备完成与实际可播状态仍以 Companion findings 和 OBS 实际音画为准；推流或录制期间不修复场景集合，不自动改全局输出设置。桌面只处理窗口和本机覆盖显隐，不复制节目状态。Companion 解析 OBS 启动路径，桌面 Host 在服务 Runtime Job 外启动独立 OBS，退出 Mizar 不连带终止 OBS。HTTP 服务就绪后，Companion 有界串行重试刷新当前 Mizar 集合内名称、类型与本机节目 URL 都匹配的 Browser Source，每个源每次服务启动最多成功刷新一次；不切换集合、场景或输出设置，关闭时取消重试。此刷新可恢复 OBS 先启动及服务重启时加载失败的页面，不能替代实际画面核对；理由见 [ADR-0024](https://github.com/Starfie1d1272/Mizar/blob/3b187e168ad755ede595eb8371bfaf5933c044fa/docs/decisions/0024-independent-obs-process.md)。

制作提示从现有状态生成；B 站查询有缓存、超时和并发上限，只服务本机状态提示，不进入公开输出或节目切换门禁。实现见 [ADR-0019](https://github.com/Starfie1d1272/Mizar/blob/3b187e168ad755ede595eb8371bfaf5933c044fa/docs/decisions/0019-production-guidance-and-platform-status.md)。

## 安全、采集与扩展

本地监听、Origin 校验和凭据分离见[协议安全](protocol.md#本地访问与安全)。采集写盘不能阻塞 GSI 接收，重放必须经过生产适配器，规则见[遥测语义](telemetry.md#采集重放与时间)。

新增数据源优先增加适配器，新增画面优先复用已有投影，新增可靠输出不改变高频快照语义。第二个真实消费者、提供方或独立发行需求出现前，不建设通用插件框架。

Desktop 的 CS2 启动、临时配置与恢复遵循 [ADR-0026](https://github.com/Starfie1d1272/Mizar/blob/3b187e168ad755ede595eb8371bfaf5933c044fa/docs/decisions/0026-managed-cs2-launch-and-restoration.md) 和 [ADR-0027](https://github.com/Starfie1d1272/Mizar/blob/3b187e168ad755ede595eb8371bfaf5933c044fa/docs/decisions/0027-cs2-launch-recovery-workflow.md)。状态查询不等待启动或退出操作锁；Steam 请求提交后立即释放启动命令锁，准备中心显示正在等待，不因固定等待时限判定失败。后台继续按 PID、创建时间与规范化程序路径认领唯一晚启动进程；等待期间不提交进入现场，保留本次进入意图，游戏被确认运行后继续打开工作台；取消请求或导航离开会取消进入意图，不重发 Steam 启动。本地服务启动失败时，Host 原生恢复入口只读取同一 SessionStore、观战恢复与试播清理记录，不调用可能自动写回的 poll；用户明确恢复后复用 ManagedCs2 原有进程、路径和读回门禁，不关闭游戏、不启动 Steam，也不确认制作结束或本场回收资格。运行中的 CS2、未知进程状态及 Demo 试播隔离拒绝离线写回；Steam 待确认要求原有显式取消确认。恢复返回的软警告同样显示原原因与下一步，不以检查完成掩盖仍待恢复的记录。错误继续保存在本机 DesktopLog，诊断导出保留脱敏的原因和 stderr。Steam 请求待确认时保留持久记录，取消等待必须先取消 Steam 请求并确认游戏关闭，再显式恢复备份。未确认启动会阻断正常退出；正常退出（含 `--stop`）先由 Host 请求 Companion 安全切场与释放数据源，再关闭受管理游戏、恢复配置，成功后才停止服务；收尾失败保留 Host，退出期间拒绝新启动与工作台进入，异常退出后的恢复状态跨窗口可见。工作台退出也由 Host 执行同一安全收尾顺序；先尝试打开准备中心，保留工作台直到收尾成功，不因隐藏或网页导航丢失任务。首次打开失败只记录本机原因，不跳过安全收尾；清理完成后释放游戏锁并重新尝试呈现准备中心，以最后一次呈现结果判定窗口收尾。准备中心缺失、取消最小化或显示失败明确返回错误，不宣称退出成功。工作台两块面板分别尝试隐藏，单块失败仍尝试另一块并保留 HUD 隐藏请求；面板隐藏失败记录本机原因，退出返回错误并允许在准备中心重试，不因制作已结束而宣称窗口收尾成功。Host 只保存此次退出的阶段、忙状态和错误反馈，准备中心与底栏只读同一结果，不复制制作或恢复事实；失败释放退出门禁，保留原始本地日志、备份、重试与诊断入口。退出开始使此前的工作台进入代次失效；现场窗口先隐藏创建，主线程把显示、聚焦、隐藏准备中心和清理旧反馈与退出开始互斥提交，已完成或失败的退出也不会被旧进入覆盖。Steam 取消确认仍显式提交给原恢复门禁。启动项只传给本次 Steam 调用，不修改持久启动项。退出请求与失败重试见 [ADR-0033](https://github.com/Starfie1d1272/Mizar/blob/3b187e168ad755ede595eb8371bfaf5933c044fa/docs/decisions/0033-host-first-exit-request.md)。

Host 持有本次启动的 MulNX 启动器进程句柄。成功关闭游戏并确认没有 CS2、且启动请求不再待确认后，先请求启动器正常关闭，超时才结束该句柄所指进程；失败保留恢复状态，不按进程名关闭外部启动器。Host 重启后无法凭旧 PID 单独取得关闭权限，未确认的启动仍要求人工核对。

工作台面板初始隐藏，进入时为保持焦点采用原生非激活显示。Tao 0.37.1 的隐藏操作比较缓存 `VISIBLE`，但可见性查询读取 HWND；原生显示不会补写缓存，后续 Tauri hide 可能不做任何操作却返回成功。因此面板的显隐都在拥有窗口的 UI 线程执行同一原生非激活路径，保留位置、层级和前台窗口，并读取真实 HWND 可见性核对结果；退出等待实际隐藏结果，读回不符不能完成收尾。此项修复针对已证明的 API 状态不对称，不代替现场锁等待、窗口调用和系统错误的逐阶段证据，也不证明所有历史退出停滞由此造成。

手动恢复旧备份由 Desktop Host 持有原生文件选择和预览。只读取当前已验证 Steam 账号的配置，界面使用本机昵称及可用的缓存头像确认目标，Steam64 仅用于内部校验；读取不到昵称时提示重新登录。原生确认重新核对账号、程序、配置与所选文件字节，以及无受管/外部游戏、无既有恢复或试播事务。先保存当前原件，再以同一 SessionStore 的版本 4 恢复记录提交字段级变更；视频只恢复已识别设置，配套机器配置只恢复 fps_max，未知内容保留。显式恢复可按选定备份消除相关重复键，不自动选择冲突值。中断后复用恢复入口，已完成的同值写入跳过，外部修改时保留原件与事务等待核对；写前复核不宣称与 Steam Cloud 构成跨进程原子事务。

可选 Steam 头像由 Companion 的本机媒体缓存提供，赛事头像优先；不修改身份或比赛文档。密钥与缓存独立于采集、预设和支持包，见 [ADR-0034](https://github.com/Starfie1d1272/Mizar/blob/3b187e168ad755ede595eb8371bfaf5933c044fa/docs/decisions/0034-local-steam-avatar-fallback.md)。

安装版的数据目录与自动准备所有权边界见 [ADR-0048](https://github.com/Starfie1d1272/Mizar/blob/3b187e168ad755ede595eb8371bfaf5933c044fa/docs/decisions/0048-installed-state-and-safe-preparation.md)：安装版使用当前用户数据目录，便携模式保持原路径；自动 GSI 不取得未知文件所有权，OBS 重连不覆盖手动配置。

桌面窗口对齐只在实际客户端范围与目标一致后确认成功。系统调用失败、画面范围不一致及保留原设置分别反馈；权限拒绝不推断为管理员权限差异，也不自动提权。窗口组恢复错误保留失败目标角色，工作台与准备中心显示同一 Host 反馈；新的成功恢复清除对应告警；手动命令保留 Host 错误归属，不在页面复制旧原因。隐藏期间完成恢复后，只有 SessionStore 核心记录已清理且全机 CS2 已确认停止才清理窗口反馈，读取失败或仍待恢复时继续保留。诊断只投影有限窗口范围、显示器工作区、DPI、失败阶段及当前 Host／游戏提权状态，不包含窗口标题、句柄或私有路径；读取失败为未知，游戏退出后的状态不能还原运行时权限。

本机支持包以 `fullLogs` 中压缩分卷的完整保留日志为证据主体，`logs` 和 `businessHistory` 只是索引。Companion 复用 Fastify 日志和控制生命周期，记录请求方法、路由、请求与浏览器关联号、关键参数、相关前后状态、响应和原始错误链；二进制上传仅记录文件元信息、字节数及摘要，不复制音频或图片。浏览器记录 Mizar 内的控制、文件选择、原生调用及传输失败；Host 在原生分派与既有执行阶段记录实际参数、恢复和等待终态，不监视其他应用的任意活动。 可选受管 CS2 技术控制台只观察已证明本次游戏身份的固定派生文件，单独同意、跳过聊天与未知内容，不读取任意用户文件；具体读取、关闭、时间区间与预算边界见[诊断回传](diagnostics-delivery.md#受管-cs2-技术控制台)。

会话日志使用单个异步串行写入器、最多 2 MiB 等待字节、按最多 256 KiB 批量追加（单条记录更大时独立提交），单段 8 MiB、最多八段，初始化时删除最后写入超过十四天的段；实时采集不等待日志 I/O。超载、写入失败、段轮转与过期计数、序列缺口及未正常结束的会话明确导出；断电可能丢失内存和操作系统缓存，旧版本未记录的范围无法补回。原生及监督器已有四段、每段 25 MiB 的容量边界继续生效，业务历史仍按下述规则维护索引。各类当前持久文件与固定暂存的总预算约 480 MiB，另外兼容既有旧命名的三段桌面日志；既有原始比赛采集另属原采集保留策略，不为支持包读取。

导出只读取固定产品日志名，拒绝符号链接、硬链接及文件身份变化；全文件按一 MiB 解压字节分卷，用 gzip 和 Base64 保存在 JSON 内，每卷及文件提供 SHA-256。默认包含全部保留记录，可明确选择起止时间。Companion 记录既有 `MIZAR_STARTUP_SESSION_ID` 对应的启动宿主关联编号，进程自身编号区分重启与序列；`focusSessionId` 聚焦会话索引，原记录继续包含时间范围内的跨进程来源，以保留借用运行时的证据；无法归属时间的旧文本仍保留。读取状态、实际字节、会话首末时间、序列及终态随包提供。最终传输预算为 256 MiB，超出时明确失败并要求缩短时间范围，不删掉若干事件后宣称完整。密码、登录令牌、Cookie 与推流密钥按字段或值精确替换；保留技术路径、文件名、业务身份及诊断所需配置，不读取任意私人文件。用户主动保存后私下交付维护者，默认不自动上传。回传同意、可靠待传队列、当前实现阶段与零付费边界由[技术诊断回传](diagnostics-delivery.md)唯一维护；本机支持包完整性不能推定为云端已完整接收。

可选 Steam 头像配置和缓存加载失败保留读取、解析或校验阶段及异常，文件缺失沿用首次使用流程；配置 JSON 的凭据片段从解析器报错中替换，保留错误位置和技术路径。

系列进度检查点和 HUD 配置的读取、解析与持久化失败保留原始异常链及目标路径，沿现有本机日志进入支持包；HUD 文件读取失败与内容校验失败使用各自原因码，恢复时继续保留原文件和已有有效状态。

原生日志采集只读取受信任日志目录内固定的 Host 日志名称及游标文件。Windows 包路径映射使单个文件的系统解析路径落在目录解析路径之外时，分别复核逻辑目录和解析路径的祖先、普通单链接文件以及两种路径的文件身份；打开后再次比较句柄与逻辑路径身份。此例外不适用于调用方提供的任意路径，也不改变资源 Store 的包含关系检查。

业务诊断由现有投影、RivalHub 请求结果与发送队列的持久提交提供事实，索引独立保存为 `logs/business-history.json`；同一事实在索引轮转之前同步送入完整会话日志，已有聚合规则保留首末时间、次数及原因变化的检查点，索引容量不截取主操作日志。业务诊断不作为比赛、恢复、授权或自动重放的状态来源。按比赛与制作会话分组；上下文、地图执行、比分、身份、名单、覆盖状态和新鲜度发生变化时记录摘要，普通游标推进不逐帧写盘。认领尝试、HTTP 结果、开局可靠确认、LIVE 接收变化以及可靠事件入队、重试、拒绝、过期和恢复分别记录；远端 JSON 解析或读取失败向浏览器和业务索引传递固定类型与错误码；转换前的原始异常链仅进入精确遮蔽已知凭据后的本机完整诊断日志，不记录完整响应正文，网络异常的公开投影只传递允许的类型和系统码，包装异常以可序列化的 `rootCauseCode` 保留已确认的根因码，业务记录的 `causeCode` 与普通日志导出再次按允许列表核对，不依赖 `Error.cause` 的对象类型恢复根因；诊断旁路失败不能改变原发送守卫或队列提交结果。

OBS 技术事件摘要继续作为索引。用户主动完整导出时，复用已发现的固定 AppData / 便携 OBS 根、日志命名和路径身份校验，仅为日志内存在 Mizar 自有捕获或浏览器来源标记的 OBS 会话附加原文；持久配置名或进程时间相关本身不足以纳入原文。不遍历其他软件或任意文件。固定选定配置中的密码、令牌与推流密钥仅在内存中用于精确替换，不附加配置正文；凭据上下文读取失败则拒绝该原文附件并标明原因。保留 CEF、性能、长行及未知技术行，不以白名单摘要替代。原文与 Mizar 日志共用 gzip/SHA-256 分卷和离线还原工具，保留来源、本地时区、读入字节和状态。OBS 导出最多两个已发现根、每根最近八个标准命名日志，仅选 24 小时内文件，单文件 25 MiB、合计 64 MiB、采集总时限沿用七秒；文件数量未选、超预算、未关联、读取失败、超时与未完整末行明确标记。时间范围筛选作用于 Mizar 时间戳记录，OBS 相关源文件整体附带以保留上下文；读取开始后的追加不属于此次快照。旧版本只有有限技术事件，不能声称已包含完整相关 OBS 原文。

性能证据每 15 秒聚合并在导出、关闭时刷新。服务端复用输入接收编号/时间、新鲜度、Recorder 有界队列和 latest-wins 投递计数，增加同步观测处理耗时、最多八个慢处理样本及各通道已发布游标/订阅者积压；处理耗时不包含上游适配器或异步发送。Mizar 自身渲染文档聚合快照消费/订阅回调耗时、首末游标、接收间隔、RAF 回调间隔和支持时的长任务计数，异常窗口仅保留最多八个样本，不逐帧写日志、不保存帧正文、不自动上传。RAF 不等于 GPU 绘制或 OBS 捕获；发布和接收游标只能帮助区分输入停滞、处理/投递积压、客户端消费与主线程停顿，不能直接证明端到端画面延迟。旧版本未采集的持续处理/渲染窗口不能补回；排查仍需对应版本诊断、原始日志和回放时间点，OBS 捕获问题另查 OBS 日志。文档关闭或断电前未送达的窗口可能缺失，不能宣称完整。

业务定位字段通过类型与格式校验后原样保留，包括比赛、地图、上下文修订、制作会话、生产者、幂等和可用回执 ID。名单仅投影核对所需的 expected/observed Steam64、参赛方、选手 ID、首发标志与槽位，以及缺失、额外和重复账号；覆盖缺失与账号差异分别保存，不把未观测到解释成已证实的名单冲突。该本机诊断边界不放宽公开实时投影。业务索引的磁盘与投影应用同一结构化字段白名单；完整操作日志另按上述凭据替换规则保留相关配置和技术上下文，不复制原始遥测或任意远端响应；远端未知原因保留 unknown。不同重启和重复导出保持业务 ID 可与服务端核对，普通日志 session 仍按导出加盐。

容量策略由 [业务历史实现](../../apps/companion/src/support/business-history.ts)维护：每组最多 512 KiB，其中普通上下文最多 128 KiB，其余预留故障；全局最多 16 组且最多 8 MiB；原子写入只使用一个最多 8 MiB 的固定暂存文件，历史与暂存磁盘峰值最多 16 MiB，旧 NDJSON 兼容文件另外保留。超限按组的最后记录时间淘汰最旧组，不设置时间到期。组内分别轮转普通与故障事件并计数，故障内嵌当时已采集的名单、覆盖与守卫上下文，作为同一条记录一起保留或淘汰，普通日志不能单独挤掉该上下文。连续相同 LIVE 结果聚合记录次数与首末观测／记录时间，不因每帧时间戳变化写入新记录；聚合次数不解释为 HTTP 请求次数。HTTP 轮询不能挤占业务历史。

实时回调只向有界内存队列入队，不执行磁盘写入或 fsync。等待队列最多 128 条／512 KiB，单个串行异步写入器按批次处理；等待中的普通运行状态可被同组较新状态替代，队列超限先移除普通记录，全部为故障时才移除最旧故障，省略数量单独计数。一个正在写入的批次另外受同一上限约束，归档仍受既有容量限制。磁盘按同目录固定暂存、异步同步与原子替换提交；重复成功不触发逐帧归档重写。正常退出停止生产者后 flush；导出最多等待当前提交与一个后续批次，不要求 LIVE 停止。I/O 失败不紧循环重试，不改变比赛或发送结果；后续采集可触发延迟重试，显式导出／退出也尝试 flush。异常退出可能丢失尚未提交的内存记录，不能称其已经持久化。正常退出、重启和升级保留已提交文件。重启时仅清理该暂存槽内的普通文件并计数，不将未提交字节冒充已采集历史；拒绝暂存符号链接。写入失败时当前快照标记 `businessLog: write_failed`。导出以已提交的磁盘历史为来源，manifest 同时合并当前进程的失败次数，分别提供已提交／未提交失败次数、等待记录与未提交聚合数量；不把仍在内存的记录冒充已落盘证据。恢复成功后这些计数随归档持久保存；进程在无法写盘期间退出，未保存的失败次数仍可能未知。损坏或不支持的历史保留原文件，停止覆盖；逐组／逐条隔离损坏并导出有效组，分别报告坏组与已知坏记录数量，坏组的记录总数不可知时标为空值。完整文件不可解析或读取失败时，导出明确标记，不能视为空历史或正常完整记录。

业务历史索引使用独立的 512 KiB 投影预算，按近期完整组选择；`fullLogs` 同时包含已保留 `business-history.json` 的完整脱敏副本，不用该索引预算截取原始记录。manifest 提供采集与导出时间范围、来源版本、写入失败、轮转、损坏与导出遗漏计数；有限窗口不声称无限完整。`originalObservedAt`、`recordUpdatedAt`、`recordedAt`、`restoredAt`、实际请求 `sentAt` 与 `acknowledgedAt` 分开；队列恢复时保留已采集的生成版本并记录恢复版本，旧记录缺失版本保持未知。队列 `attempts` 是 sink 调用次数，包含未发出 HTTP 的本地拒绝，不是 HTTP 请求次数；`restored` 仅表示从队列读取，不表示本次发送或确认。接收端没有提供独立回执 ID 时保持空值。

旧 `business.ndjson` 及三段轮转仍通过旧日志投影兼容导出；其加盐引用不可逆，版本未采集的字段与已轮转数据无法补回。新 manifest 将旧格式与未采集状态写明。导出仍由使用者明确保存与分享，不自动上传；本机 Origin 权限不变，完整日志分卷与传输边界见上述支持包契约。

RivalHub 配对配置加载分别记录 `connection_read`、`connection_parse`、`connection_validate`，启动阶段即接入服务日志；缺失文件保持首次未配对流程。JSON 错误保留解析位置与堆栈并移除凭据正文片段，非法地址仅记录验证原因。

采集故障沿用 Recorder 的结构化错误码、操作及有限系统错误码进入服务日志和支持包；当前快照保留 `lastErrorCode`。不为诊断重新启动采集或读取原始采集正文。

OBS 输出 RPC 与操作失败在支持包中分别保留 `obs_output`、`obs_output_command` 阶段及有界、脱敏的业务码、OBS 数值码和原因链；配置忙碌时拒绝输出操作也记录在同一诊断边界。摘要索引沿用原错误投影，完整日志只替换凭据值并保留上下文，不改写本机日志，不连接 OBS 或重放命令。旧支持包已过滤掉的原因无法还原。

支持包还并行读取 Windows OBS 原生证据，总采集期限 7 秒、导出投影最多 24 KiB，不启动、停止或重配 OBS/CS2。只从 APPDATA 候选目录或运行中 OBS 的 portable 目录读取已选 profile/collection，目录项最多 128、日志最多两份，取 24 小时内日志的有限头尾，仅投影最近两小时的 hook 尝试、重试、失败、成功、停止与渲染器错误。日志窗口保留最近失败；文件缺失、拒绝访问、超限和整体超时分别留下状态。配置仅投影已保存 Program（与预览分开）、分组可见性及有限捕获/视频字段；不导出 profile/场景/窗口私有名称、URL、推流密钥、配置正文或完整命令行。只读进程查询保留 OBS/CS2 PID、创建时间、提权状态（读取失败为未知），以及 CS2 第三方捕获参数是否存在；可执行路径只在内部定位 portable 目录。日志与进程仅按时间关联，不能当作 hook PID 证明；已保存配置不等同于当前 Program，hook 成功和源尺寸不证明当前像素正常。可选采集失败保留普通支持包，旧包缺失的原生日志无法补回。 读取前核对完整祖先及下级路径，拒绝 junction/symlink；打开后以 ino/dev 核对文件身份并复核路径身份。portable 兼容官方四种存在性标记。原生事件分类保留 helper 十进制退出码、DLL/plugin hook 版本，以及 D3D11 HRESULT 十六进制值与数值；不依赖错误正文一定包含 fail/error 关键词。JSON 最终 UTF-8 大小仍超限时返回明确 export_budget 截断后备状态，不输出超限投影。

### 解说 CFG 与键位恢复

维护一份 `mizar_observer.cfg`：数字键 1–9、0 对应武器槽选择，H 切换 CS2 原生 HUD，`spec_usenumberkeys_nobinds 0` 启用对应观战选择。标准 Steam 启动（含保留画质）、Demo 和 MulNX 自动启动均请求执行同一文件；Demo 另用会话临时文件播放所选录像。实际游戏加载顺序、键位生效及退出写回仍待 Windows CS2 实测。标准启动时 HUD 初始状态保持游戏原状。MulNX 自动隐藏开启时，Host 先读回并保存当前 HUD 原值，再在本游戏实例首次连接准备中提交一次隐藏；提交前持久记录尝试，未知结果或重试不再次覆盖 H 的人工操作，结束时恢复原值。按键由 CS2 原生处理，不通过网页 HUD 或 OBS 控制。

Host 在游戏启动前检查当前账号的 slot0 主键位文件，并保存受影响数字键、H 候选及原观战变量的原值；空值与缺失分开记录。只有可唯一识别 `h` 或 `scancode11` 时，才在同一 CFG 中输出该固定键名；两个候选均缺失时使用标准物理 H 的 `scancode11` 并记录缺项；冲突或重复时保留数字键功能并说明 H 未接管。同名文件仅在字节完全匹配受管理版本时升级，未知文件与链接不覆盖。启动前复核原绑定并持久标记可能加载；退出后只恢复本次所写字段，若当前值既不是原值也不是受管值，或键身份发生变化，保留当前文件和备份供重试。运行时 HUD 显隐值不承诺恢复。

Steam 可能在本次启动参数之后执行个人 CFG。Host 在有界读取 `autoexec.cfg`、Steam `+exec` 和同步引用后，于这些启动文件末尾临时追加固定解说 CFG 的执行命令，避免 `binddefaults` 或个人 H 绑定覆盖本次配置；不修改 Steam 持久启动项，也不执行读取到的命令。正常模式复用帧率文件事务，保留画质与 MulNX 模式复用观战恢复记录且不修改帧率。原件先落盘，再应用并读回核对；取消、失败和正常退出均恢复原文件，外部改动保留备份并阻止覆盖。异步执行、自定义别名调用及直接修改键位的 Steam 参数无法保证顺序时拒绝该接管，不把提交启动请求当作键位已生效。

MulNX 自动启动通过其现有 `launchOptions` 临时追加同一个 `+exec`，绑定确认后的 PID、创建时间与程序路径；启动项清理不覆盖用户新修改。借用游戏不会由 Mizar 强行关闭，键位恢复记录保留至游戏退出后重试。两种启动方式均由 Mizar 管理解说配置；自行启动的游戏须退出后重新从 Mizar 启动，不提供手动准备 CFG 或通用借用入口。启动前已有的受影响键位按同一恢复事务保存。

不再为新启动创建全键位配置或提供完整键位选择。已存在的完整快照和旧版观战恢复记录继续按各自版本恢复，保留身份、进程停止与冲突门禁；不得因迁移清除待恢复记录。多文件和 Steam Cloud 不构成原子事务。来源资料：[Valve 2024-02-15 更新](https://store.steampowered.com/news/app/730/view/6856237235656946987)、[SDL scancode 定义](https://github.com/libsdl-org/SDL/blob/main/include/SDL3/SDL_scancode.h)。

## 可选地图运镜编排

选择 MulNX 启动时，进入工作台的同一次用户意图通过启动器消息总线发起一次请求；安装位置仍由 Host 发现，Companion 只准备受管工具及配置。入队回执不代表启动成功；Host 核对实际游戏的 PID、创建时间、程序路径和游戏内网关监听进程，再绑定受管配置事务，并在制作进入现场前以当前制作修订建立原生运镜租约。Host 持有已验证的游戏进程句柄，每两秒续约；实例退出、不再唯一或续约失败时隔离租约，结束游戏时撤销租约。若撤销结果未知，Host 在停止续约后等待超过两个六秒租约周期，以覆盖一个可能迟到的在途续约，再继续原生游戏收尾；已确认服务停止时可直接继续。该等待不替代 MulNX 卸载核验。明确借用的外部游戏沿用借用语义，不授予进程关闭权限。启动结果未知或实例变化时不进入制作，Host 接入前必须核验本机持久化的 Mizar 进程记录；完整启动流程及上游能力边界见[地图自动编排](orchestration.md)。

Companion 的 `orchestration/` 消费既有 Program 投影、音乐阶段分类和实际开场 Take，保存本机地图预设，调用隔离的 MulNX WebSocket 适配器。Core、Program Director 和音乐模块继续拥有原有事实及职责；预设不进入公开投影。连接、人工保持和 Cue 为本进程临时状态；连续性变化保留人工或自动选择，但使准备状态失效，重新应用本图包并回读后只等待新事件。新阶段只允许一个有期限、绑定上下文的清空后交接；隔离包磁盘验证为调度前提，自动和手动播放均需活动包与空自动列表回读；该回读不证明资源加载。Host 内部沿用查询句柄管理唯一且与本机进程记录匹配的 MulNX 游戏；该内部借用不授予进程关闭权限，不修改画质或布局，启动阶段的解说配置另有恢复事务。实际制作收尾后只解除借用，不关闭外部游戏或授予停机回收资格；重启必须重新确认。实例退出或不再唯一时使借用失效并撤销 Companion 原生控制许可，失败后重试隔离，不重发镜头。Companion 持有 Host 启动/借用代际及六秒单调时钟租约，Host 两秒检查后续约；超时、Host 重启或制作收尾锁定 connect/resume/audition 与自动调度，迟到心跳不恢复。新 Host 呈现前撤销旧原生会话；产品 Companion 重启默认待确认。浏览器备用模式仅在制作准备阶段显式选择，之后独立于 Host 生命周期，不被旧原生消息撤销。入队与执行证据分离、过期保护及剩余上游缺口见[地图自动编排](orchestration.md)。

退出工作台失败时，Host 保留原始退出结果，并复用居中、聚焦的原生核对窗口展示 `kind=exit`。此窗口仅在存在退出异常时允许打开，不受工作台隐藏状态限制；它读取 Host 退出状态，提供返回准备中心处理与运行诊断入口，不直接重跑收尾。配置恢复按钮按游戏是否已关闭和失败阶段命名，外部 CS2 接入不显示无关备份入口。

核对窗口关闭命令只授予 `tool-review` 窗口；Windows 原生 IPC 按来源而非页面路径匹配本机权限，命令自身仍核对窗口身份。

OBS 音频分路绑定属于本机操作员配置：游戏、远端解说和麦克风由操作员从当前 OBS 来源中明确选择，保存 UUID、类型和场景集合，并在读取及变更时重新核对。候选短期有效，修订号阻止旧窗口覆盖新绑定。完整绑定启用后，自动准备将三个角色接入全部 Mizar 场景，并关闭这些场景内其他直接音频引用；不更改共享来源的设备、增益、滤镜、监听或音轨，也不改其他场景。全局音频、启用的嵌套路径及未绑定的画面附带音频无法仅靠直接引用安全排除时保留待处理状态。实际设备、音轨和监听回灌仍需在 OBS 核对并录制试听。

声音设置提供独立分路和桌面混音切换。桌面混音优先复用上次有效来源，其次复用受管场景中的播放设备音源，无候选时创建禁用的默认设备来源；多个不同设备需选择。桌面模式不要求游戏或解说已有绑定，保留有效麦克风及其关闭状态，在所有受管场景停用游戏和解说分路并保留麦克风；游戏与解说共同受桌面音量控制，中场游戏策略暂停。切回时恢复已保存的角色绑定；缺少独立配置时自动准备，解说应用未运行时保留桌面混音并等待，用户可取消等待。场景引用变更继续使用迁移记录；切换意图保存目标、关联 ID 和音乐恢复元数据；场景项、独占画面附音和音乐监听写入同一迁移记录。保持观察的连接上先回读并核对身份与字段阶段：目标完整时提交目标，部分写入时恢复来源侧；音乐元数据与模式提交后才清理未决记录。无法确认或发现外部修改时保留记录，不将未完成状态当作成功。直播或录制期间也可切换，不发送停止输出命令；匹配目标的全局桌面来源或麦克风可复用，其他冲突全局来源与跨非受管场景共享的音频路径仍须处理；受管独占嵌套音频与画面附音由迁移记录恢复。桌面采集和 OBS 监听设备相同时，受管音乐的监听与输出改为仅监听并由桌面采集；切回时仅恢复仍保持该状态的受管音乐来源。桌面混音中新增受管音乐也按同一设备关系选择默认监听，并记录切回时的恢复状态；不同设备保持原监听路径。一个设备使用默认值、另一个使用具体设备时若无法确认关系，受管音乐保持节目直出并保留监听偏好；独占麦克风监听可能回灌时自动记录并关闭，切回时按仍持有的记录恢复。共享监听来源须先排除具体冲突。设备变更、音轨和实际输出仍需录制试听。

场景自动准备在 OBS 未输出时识别唯一 TeamSpeak 来源，并在 Mizar 场景的直接音频路径通过核验后准备独立游戏与解说来源。所有受管场景共用各自的来源，先启用新引用再关闭旧桌面引用；迁移使用同一 OBS 连接观察身份、输出和人工变化，未决记录保留供核对。尚未启动的 TeamSpeak 在启动后继续完成准备；人工更改偏好后旧等待请求失效。迁移完成后为从未配置的音频分路保存游戏、解说和麦克风绑定，已有人工选择及解除绑定优先。其他场景中的自定义来源不阻碍准备；Mizar 场景内的旧直接混音纳入迁移，唯一已有的自定义麦克风优先复用。成功事务保留切换前后引用与端点、集合的备份，未知结果保留未决记录；多个麦克风或不可识别路径不猜测选择。重复检查已迁移场景时重新核对来源身份与引用，不重放迁移。自动准备只以连接、输出与视频设置变化触发，检查结果差异不重新触发写入，避免阻塞 Demo 试播。

设置中的“选择其他应用”读取 OBS 应用音频窗口候选，保存时重新核对连接、场景集合、偏好修订和候选；选择保存在本机，重启后继续优先使用。所选应用暂未运行时保留旧声音并等待应用出现；恢复自动识别 TeamSpeak 需要用户显式选择。Mizar 自有来源最近确认的目标独立保存，不因偏好停用而丢失；显式改选时核验该目标、UUID 和修订，停止输出后再次核验并观察变化，再写入新目标和读回。发送后结果不明时保留记录，不自动重放；无法证明来源归属或旧目标已变时提示核对，不自动覆盖。

中场游戏音频策略默认保持。操作员可选择降低音量或静音，仅作用于明确绑定并经当前 OBS 端点、集合、UUID 和类型核对的游戏来源；解说、麦克风和音乐不受该策略修改。策略以可信比赛状态驱动，逐字段保存原值、写入值、操作、绑定修订与连接代际，并持续观察 OBS 音量和静音事件。人工改动、断线或身份变化时让权；未知写入结果不重放，进程重启后待人工核对并恢复自动控制。OBS 不提供比较并交换，外部并发修改与控制请求之间仍可能竞争。
