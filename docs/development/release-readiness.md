# 版本与发布

本文维护 Mizar 的**长期发布约束与操作原则**；具体版本的进度、验收报告、变更列表和已发布资产分别由 GitHub Milestones、PR、[Releases](https://github.com/Starfie1d1272/Mizar/releases) 持有。当前发布实现以 [CI](../../.github/workflows/ci.yml)、[Release Qualification](../../.github/workflows/release-qualification.yml)、[Release Promotion](../../.github/workflows/release-promotion.yml) 和 [Box Sync](../../.github/workflows/box-sync.yml) 为准。

Box 文件上传使用原生 HTTPS 和完整 multipart 请求体，沿用十分钟总期限，不受 fetch 独立的五分钟响应头期限提前终止。记录请求体写出与响应阶段，不记录临时地址、凭据或服务器正文；上传不自动重试。中断后先核对已存在文件的原字节，缺失文件才上传；完整回读与来源验证完成后才发布更新指针。

性能计时区分完整工作流、首次 runner 排队和重跑排队；重试及流程间等待仍计入端到端时间，不把最新尝试的启动时间当作首次排队。内部资格汇总与晋级使用同步 ZIP 解压，之后仍完整核对 payload；便携及安装验收保留 Windows 资源管理器解压。解压性能对照必须使用固定原 ZIP 与来源证明，每次核对完整 payload；额外基准不能代替普通完整 CI 或新版本十分钟发行验收。

## 版本与兼容性

应用版本遵循 `MAJOR.MINOR.PATCH`；正式标签为 `v<应用版本>`，有风险的新能力可按需要使用 `-alpha.N`、`-beta.N`、`-rc.N` 预发布版本。不要为每次小修改单独发布一个 RC，也不能因为改动小就省略必要的验收。

发布基础设施接受纯稳定版本及 `alpha.N`、`beta.N`、`rc.N`，数字不带前导零，预发布序号 `N` 为正整数（从 `.1` 开始）。所有预发布沿用 main 的 Qualification / Promotion 门禁，精确标签、源码、二进制版本和原始签名必须一致；GitHub 标记为 prerelease 且 `latest=false`，不生成 Stable 更新清单、发布确认或索引，也不写入 Box Stable、Downloads、Updates 或 Archive。Box 自动与手动触发均显式报告预发布跳过，后续稳定版计时及其 artifact 上传一起跳过；不将缺失计时证据改判为成功。资源兼容性使用去掉预发布后缀的 Core 版本，授权仍绑定完整版本及原始资产。

预发布只从对应 tag 人工下载完整 Setup 或 ZIP；稳定更新器仍只选择纯稳定版本，`channel: stable` 与 WebInstaller 的稳定限定不变。本轮不提供自动预发布渠道、独立应用身份或并存配置；安装版沿用现有安装和用户数据位置，升级、回退及数据兼容性须按目标版本验收，不承诺可与稳定版并存。脚本与 CI 检查不能替代 Windows / CS2 / OBS 实机证据。

| 变化  | 版本选择原则                                                               |
| ----- | -------------------------------------------------------------------------- |
| Patch | 与已有公开契约兼容的缺陷、安全或小型展示修正                               |
| Minor | 向后兼容的新能力、扩展和较明显的用户体验改进                               |
| Major | 公开契约出现不兼容变化，或产品进入需独立评审兼容性与迁移策略的重大版本阶段 |

路线图中的产品阶段是**演进目标**，并不自动决定技术改动的版本号。内部 HTTP/WS 协议、第三方 Provider、文件格式应按各自公开的兼容承诺版本化；不得以应用版本号代替协议兼容校验。

构建的应用版本须有单一权威来源，并与桌面配置、锁文件、发布标签和产物元数据一致；当前以 `apps/desktop/src-tauri/Cargo.toml` 的 `package.version` 为权威，通过现有版本检查验证其他副本。

## 正式发布不变量

1. **确定唯一构建身份**：可晋级候选只从 main 的资格工作流创建；输入精确 SHA、checkout、工作流上下文和签发前的产品 manifest 必须一致。晋级核对成功资格任务的 main 与精确源码，并通过 GitHub CLI 同时验证 main 签发工作流、来源 ref 和来源 SHA；客户端信任条件不放宽。冻结源码 SHA 和版本，所有验收、构建、安装器与公开文件均能追溯到这一身份；修复后重新评估受影响的验证范围。
2. **先验证再晋级**：候选应通过当前必要 CI、契约/回归验证和 Release Qualification；正式发布只晋级已经核验过的资产，不在晋级时重新编译另一份“看似相同”的程序。
3. **按风险做实测**：CS2、OBS、Windows 宿主、GSI/CSTV、安装和更新的变更须在相关真实环境验收。普通文档变更不需要重跑整场比赛；浏览器模拟也不能冒充原生性能、OBS 捕获或安装验证。
4. **安装与回滚可信**：验证升级、卸载、运行中阻断、带空格路径和用户数据保留。新版失败不能无提示销毁旧数据；任何不可逆迁移必须在发布前说明与验证。
5. **保留供应链证据**：记录源 SHA、产物身份、依赖/许可、SHA-256、资格构建与完整性验证。签名/证明的存在与验证结果须以当次发布事实为准，不能仅凭下载页写有散列值就宣称来源已认证。
6. **明确上线后的状态**：版本、变更、兼容性/迁移事项、已知限制与下载入口记录在本次 Release Notes。历史发布说明不因下一次发布而改写。

Windows 安装版与便携版属于不同的分发形态，用户数据路径和升级/回退语义也可能不同；当前操作步骤以[快速开始](../guide/quick-start.md)为准。交付名、发行清单和内容摘要遵循现有 qualification / promotion 脚本，不在这里复制一份易失效的构建参数列表。

## 发布过程

| 环节     | 核心要求                                                                                |
| -------- | --------------------------------------------------------------------------------------- |
| 候选     | 固定来源和版本，给验证者提供安装/便携资产、变更范围、可复核证据；必要时做真实现场短实验 |
| 资格构建 | 对精确源码执行必需 CI 与打包/安装、启动、升级、内容身份检查，保存报告                   |
| 正式晋级 | 对比候选与最终源码，验证同一套合格产物，发布前核对标签、清单、下载和许可                |
| 发布后   | 从公开入口下载复核，与既有版本按需做升级/回退检查，记录异常和修补版本                   |

资格工作流只创建一次正式 Windows 产品；portable、Full Setup 与 Core Setup 独立并行验收同源候选，Full/Core Setup 复用同一准备 helper 并行安装固定 NSIS 与 Explorer 解压，等待两者成功后才执行后续恢复及安装验收，汇总要求三条身份与安装恢复证据，分发 artifact 文件互不覆盖。晋级校验并发布原始合格资产，不重新编译。`cargo test --profile release` 编译原生契约测试，不能仅因它位于产品构建之后就视为重复产品构建并删掉。打包、安装、GUI、恢复与来源身份仍须分别通过。发行计时以 Qualification 触发至 Box 最后原字节核对为完整范围，包含晋级、流程间等待和 runner 排队；缓存命中情况与恢复运行单独记录，旧版本恢复及缺失计时不能作为新版本 ≤600 秒的验收。

正式 Cargo release profile 使用 Thin LTO、16 个 codegen units 与 strip；CI profile 保持独立，Cargo 缓存身份包含 compiler profile。Full 与 Core Setup 共用 NSIS Zlib，分发身份仍绑定实际安装器脚本摘要。有限 Windows 对照中，热构建平均减少约 88 秒，Host 增加约 1.47 MiB；Full 安装器增加约 14.54 MiB，编译与安装明显缩短。实际 CI artifact 下载与安装已核验，但未测 Box 跨境下载增量，GUI 采样也不能证明零启动退化。参数变更后仍须实际验证正式 Thin 构建、两种 Setup 的安装、卸载、恢复与 GUI；完整 ≤600 秒以随后明确授权的新版本发布终验，不能用历史恢复或拼接实验耗时代替。

Cargo 或 NSIS 参数实验使用不可晋级的独立产物，同一源码、工具链与 runner 对照，明确 target、下载依赖及打包输入的冷热状态。重复试验轮换顺序，分别测量编译、安装与完整生命周期，并同时报告体积及实际下载体验。单轮成功或按带宽假设估算的下载时间不能独立决定正式参数；实验报告不替代冻结候选的 CS2、OBS 与升级恢复验收。

原生恢复资格验证在子进程及其输出流关闭后检查结果；恢复登记断言失败时保留脱敏的恢复 stdout/stderr 与注册表读取错误。诊断不替代原恢复登记、路径和结果断言。

CI 的 Windows 宿主编译测试与更新恢复验证在两个独立 runner 上并行执行，避免原生全局对象互相干扰；同一 planner 条件选择两条支路，汇总要求整个矩阵成功，完整来源证据分别要求宿主与恢复任务成功。恢复场景、截图和断言不减少，完整计时仍包含排队及汇总。

安装器故障验证的原生 UI 测试与截图可和 Node/App 依赖准备并行；NSIS 写入前必须等待原生 UI 支路成功，任一准备失败仍等待所有已启动支路结束。生产 SDK/Store/App 和 NSIS 安装验证继续保留原顺序及断言。

安装器矩阵分别验证已有安装更新、Core/App 恢复链及全新目录的身份不符／取消清理。三条支路使用独立 Windows runner，保留原 15 个案例和各自顺序；汇总核对全部三组精确源码与运行身份，缺失或失败不能由其他支路补齐。

浏览器分片沿用整文件隔离与 FULL 身份全集验证，耗时权重从注明精确源码和任务的成功日志更新；权重只决定分配，不减少测试。容器初始化、排队及汇总继续计入完整 CI 墙钟。

发布流程失败时不得通过跳过真实门禁或改写正式标签掩盖问题；先修复根因，再生成新的可追溯候选。遇到功能性/安全性问题时，可发独立 Patch，不等待其它版本主题完工。

晋级重试先核对标签及来源，逐个验证已存在资产的元数据和实际原字节，然后只补缺失资产；不覆盖同名不同字节。草稿或已公开但尚缺索引的 Release 可继续补齐。资源签发后的原字节暂存于本次晋级 CI artifact；资源证明已部分公开时必须从原记录恢复完整授权，不能重签混配。全部运行时资产验证通过后生成发布确认并上传单个 v2 更新索引，再验证原双签名。验收记录留在 CI artifacts。

独立官方资源同样消费冻结候选，不触发第二次 Core 编译。资格阶段构建真实 Pack，并将 `resource-descriptor.json` 绑定到 Core 版本、精确源码、原 ZIP 摘要、资源兼容范围、序号、有效期和固定下载地址；资格 main 工作流分别证明描述符与 Pack。操作者必须显式提供独立资源版本和递增序号，资源内容或源码身份变化时使用新的资源版本。

晋级在本次 main 精确源码的独立工具 worktree 中构造 `resource-publication.json` 与 `resource-catalog.json`，绑定原资格描述符摘要和实际晋级源码，并由既有晋级工作流签发证明。资格源码与晋级源码可以不同；原 Core、Pack 和资格证明保持原始字节。公开资产包含 Pack、描述符、目录、发行声明，以及描述符／Pack 的资格证明和目录／声明的晋级证明，共八份。客户端必须先从可信 Core 身份约束资格描述符，再验证 main 晋级目录的真实证明，之后才能使用目录策略和共享双证明验证器；镜像自报的目录、SHA 或 `trusted` 字段没有授权效力。

带资源接线的资格源码必须提供原资源 artifact，缺少资源、证明或兼容内容直接失败。历史资格源码没有接线时继续消费原历史候选，不补签或重发旧资产。已有 Release 的重试读取并验证原目录、声明、全部证明和公开资产身份，拒绝覆盖、重新签发已公开授权或降级；公开后逐项核对八份资产的唯一名称、大小、摘要与固定地址，通过后才进入 Stable 发布确认。Core-only 开发产物仍不可晋级；正式拆分分发必须由 Core 消费者实际集成可信目录与 Resource Store，并通过真实安装、恢复及离线验收。

共享发布身份入口串行执行 gh provenance 验证，资源归档与声明也等待上一进程结束，避免同时初始化默认 TUF 缓存；失败立即阻断后续 subject，不新增重试。每个 subject 继续绑定固定 main signer、source-ref、精确源码和原 bundle；初始化失败保留 verbose 原因并脱敏凭据及签名 URL。并行下载不等于并行签名验证。冻结快照中的同一资源归档与声明只验证一次原证明，当前 Core 的资格描述符和晋级目录仍分别验证；不以旧阶段结果替代新快照或不同角色的授权。

## 分发、镜像与应用内更新

GitHub Releases 是完整正式资产、版本历史和溯源信息的公开入口。国内镜像可以提供更便捷的稳定版安装包，但必须与已经通过资格验收的原始资产**字节一致**，并在可验证后替换 Stable 入口；历史回滚文件与公开分享权限独立管理。国内下载入口见[快速开始](../guide/quick-start.md)。首次迁移仅在现有原正式版本上执行 Box Sync 的 `sync`，不创建新 Release；`verify-downloads` 只读核验匿名目录及两份下载的完整原字节。需要恢复旧目录入口时对同一 tag 执行 `rollback-downloads`，先验证 Stable Full 与原完整 ZIP，再恢复原轻量 EXE，必要时将同版 ZIP 移回 Offline；不清除 Downloads 目录或 Archive、不改更新指针。旧书签和已发客户端的裸分享地址继续打开 Stable，迁移后可进入 Downloads；下一版本客户端与新公开指引直接打开用户子目录。迁移前匿名 Downloads 返回 404，不能宣称已上线。首次迁移或尚无已发布指针时匿名下载两个完整原文件；常规发布只匿名完整下载轻量 EXE，ZIP 验证匿名目录身份与 Range 可达性，其完整摘要仍在同步与最终发布边界核对。每个新 ZIP 仅上传一次、可信回读两次，不新增 Offline 副本；同版重试不上传大包，首次迁移复用已验证服务端移动。`verify-downloads` 始终执行完整匿名下载，用于正式验收，不把关键路径预算估算当作 ≤600 秒结果。

如果产品提供应用内更新，必须先验证更新元数据与来源身份，再核验安装包；**从同一不受信任来源同时获取文件和 SHA-256 并不足以证明发布者身份**。更新应明确区分安装版与便携版，正常退出后安装，不得在 Live 播出时擅自终止程序；网络、校验、安装或恢复失败时保持已安装版本可用。

轻量安装器首屏展示安装位置，首次安装可更改为安全的空目录；已登记安装沿用原位置，升级不迁移目录。完成页提供打开安装位置。新安装的 pending 恢复绑定同一安装器与原选定目录；更新准备记录与日志都证明未启动写入时可重开，启动歧义或活跃写入保留现场。恢复时先分别核验备份和当前目录；若当前目录已是完整旧版本，不再复制另一份完整恢复目录。恢复保留被换出的失败目录；错误诊断记录原始原因链和阶段，经脱敏后可复制、导出。

Stable 资格构建从原分发清单生成并证明 `update-manifest.json`，晋级核对精确源码和元数据后上传原资产。正式 Release 实际公开且完整原资产核对通过后，main 的晋级工作流生成并签发 `update-publication.json`，与原更新清单、两份原证明一起装入 `update-index.json`；资格签名不承担正式发布授权。冻结正式版本时同步 `scripts/qualification/update-release.json` 的版本和兼容范围，并完成 [CHANGELOG](../../CHANGELOG.md) 对应版本的正文；预发布版本不提供 Stable 更新清单或正式发布确认。来源身份分别绑定 main 的资格和晋级工作流，签名根由 Sigstore TUF 管理。没有更新清单的历史版本继续通过正式发布页下载；首个支持应用内更新的正式版本仍须手动升级后才能使用该能力。详细流程见[更新契约](../reference/updates.md)。

所有写入与归档完成后，发布指针前的独立完整 SHA256 回读每批最多三个并行，记录该阶段耗时；任一失败须等待同批在途读取结束，不启动下一批、不提交 latest。校验次数、大小和摘要判定不变，不复用写入前的哈希或以匿名 Range 代替完整回读。

Box 独立的 Runtime、Resources 与分发传输可并行，任一路失败须先等待其余写入结束，不发布更新指针。共享 Stable 的 Full 与用户 Downloads 串行执行：Full 完成原字节校验和归档后才更新用户入口，首次迁移的原有顺序与回滚边界保持。原素材未变时，从原版本技术目录校验并服务端复制同一 ZIP，保留旧客户端路径，复制后和发布指针前仍完整回读；不改原始素材来源。复制接口返回 405/501 时，先重新列出目标，存在的目标必须完整核验，仅目标缺失才上传已验证原 ZIP；404 无法证明接口不支持，响应不明时同样停止，并在同版重试时校验已落盘内容。

Box 小型 JSON API 与上传均使用原生 HTTPS，按调用者总截止时间等待连接、响应与响应体，不叠加 fetch 的独立建连截止。API 响应限制为 2 MiB；重定向和未确认的写入不自动重发。只读 GET/HEAD 遇到允许的暂态网络错误、请求总期限超时或临时 HTTP 状态，最多请求三次，分别退避一秒、两秒；每次沿用原请求总期限。非成功状态收到响应头后立即释放正文并按 HTTP 状态分类，不让慢错误正文变成可重试的期限超时；成功正文的真实断连保留原生暂态分类，超限主动销毁保持终止。日志只记录安全错误类别、HTTP 状态与尝试次数，不记录地址、凭据或正文；权限拒绝、未知错误和无效 JSON 不自动重试。下载与原签名验证保持既有路径；同版恢复先核验已落盘原文件，不以盲重发写入或放宽发布门禁处理连接故障。

## 更新日志与发布正文

[CHANGELOG](../../CHANGELOG.md) 是用户变更与版本特定升级说明的唯一来源。各版本按新到旧排列，标题使用 `## [1.1.0]` 等精确版本号，可用 `## [Unreleased]` 暂存未冻结变更；发布时必须存在唯一、非空的精确版本正文。保留历史变更，已发布原文与资产继续由 GitHub Release 和 Git 历史追溯，不再维护单独的版本文档。

正文只使用 `###` 分组标题、段落、无序列表（最多两层缩进）或顶层有序列表；行内支持加粗、斜体、单反引号代码与 HTTPS 链接。不使用图片、HTML、表格、引用或代码块。`scripts/qualification/release-notes.mjs` 负责唯一提取与转换：GitHub 保留正文 Markdown，固定追加版本下载链接、使用手册、发行文件与构建校验信息；应用内使用标题和段落保留、无序列表转为 `•`、行内标记去除、链接只保留文字的纯文本。未支持格式明确报错，不在客户端另写转换或渲染逻辑。

版本、源码和资格任务链接由实际构建身份自动填入，固定发布者签名说明随分发政策变化维护。更新清单在资格构建时包含转换后的纯文本并签发来源证明；正文变更必须重新资格构建，不能在晋级时替换已签清单。生成 GitHub 正文供审阅可运行 `node scripts/qualification/release-notes.mjs <版本> <精确源码SHA> <资格任务ID> <输出文件>`；生成文件不代表已经发布。

镜像上传凭据只用于发布工作流，不进入客户端、公开文档或可下载产物。正式版本号、签名状态、自动更新能力与安装说明以对应 Release 和当前用户手册为准，不在本长期规范中维护每次发布的临时状态。
Box 的 Stable 保留旧客户端必需的最新 Full Setup；Stable/Downloads 是用户入口，只保留一个同源同版轻量 WebInstaller EXE 和完整离线 ZIP。首次迁移将 Offline 同版 ZIP 原字节移到 Downloads，后续 ZIP 直接同步到 Downloads；Offline 历史内容保留，Runtime 存放现代客户端后端；Archive 归档历史分发文件，Updates 存放应用读取的签名清单信封。当前分享绑定 Stable，用户入口使用同一分享的 `?p=/Downloads` 子目录参数。必须完成原字节校验、历史归档和真实匿名下载验收后，最后发布 Updates 的最新清单。客户端专用只读 Token 仅访问公开发行资料，与发布上传凭据分开管理；具体信任和回退规则以更新契约为准。

## 发行消费者与运行时依赖

| 消费者         | 实际需要                                                                                | 保存位置                                    |
| -------------- | --------------------------------------------------------------------------------------- | ------------------------------------------- |
| 用户           | 推荐轻量安装器 EXE；同一已验证 Core 与资源组成的完整离线 ZIP                            | GitHub Release 与 Box，国内优先 Box         |
| 安装和更新程序 | Core 后端、原版本/分发清单与许可证、原 v2 双签名更新索引、资源归档及其原始目录/签名材料 | 同版本机器运输载体；Box 的 Runtime 技术目录 |
| 维护者         | 截图、测试报告、资格/晋升记录、安装器构建报告                                           | CI artifacts 与 CI 运行链接                 |

机器运输载体只聚合程序必须读取的原始字节，不建立新信任根，不装验收报告，也不创建永久技术 Release。资源 ZIP 单独运输。载体和所有读取端检查大小、白名单路径、重复条目、规范编码，解出的原字节仍由原签名验证。分散元数据附件不是常态发行目标。

v1.1.0 实际源码固定读取 GitHub 的 update-manifest.json 与 NSIS 更新后端；Box 固定读取 Stable 下的 Setup.exe。必须先真实发布支持新读取合同的桥接客户端，再在后续正式更新的签名兼容范围中排除 v1.1.0，才能移除旧清单或移动其后端入口。在此条件达成前保留最小旧客户端入口，不建立长期兼容 Release。

推荐安装器只安装不含可选 EPL 媒体的正式 Core，然后通过唯一 Resource Store 获取首次资源缓存。同次 Qualification 先完整核验 Full，再分离并重新完整核验 Core 的独立身份；各自签名，不改原 Full/已签 Core。过渡离线 ZIP 保留原 Full 的已验证离线行为，旧客户端升级保留原 Full NSIS；不要求首次启动新增 TUF 验证。真正同 Core 离线组合仍需独立资格验收。开发 core-only 与 readiness 不能通过改标志代替实际证据。

现有 SDK 的历史缓存 receipt 从固定 Sigstore seed 核验原签名，允许已经安装的资源在 TUF 元数据过期后继续使用；这不等于允许冷机器首次安装。首次离线验证的前置接口补充原始 timestamp、snapshot，并检查 root 授权、角色版本/摘要绑定及各角色有效期，沿用同一 SDK 信任根。该接口不提供永久离线首次安装资格，尚未启用到发行或 Store 安装路径。

长期离线 ZIP 的关键依赖是明确首次安装的信任合同：若沿用在线 SDK 的 TUF freshness 要求，过期离线包必须更新；若要求长期冷机器断网首次安装，则需要在现有信任体系内单独审定可授权该行为的合同，不能把新安装改称缓存恢复。旧版本只读 Box 验证、真实旧签名的断网前置验证与 UI fixtures 均不冒充新产品安装验收。readiness 必须以真实产品资格与安装证据为准。

Promotion 对同次已成功资格任务的产品和验收证据并行下载到独立目录，两者全部完成后才校验来源与证据；任一失败阻断后续。产品各项 provenance 逐个复用原始 `qualification-provenance.json`，仍绑定 main 签发工作流、精确源码 SHA 和每个资产字节；缺失或无效 bundle 直接失败，不回退到放宽校验。证明核验的性能对照应固定原资产与证明，记录失败及包含准备时间的总墙钟；测量不替代全流程十分钟验收。

Release Host 的原有 `cargo test --profile release --locked` 在 exact-source build 成功后作为独立支路，与三个安装／便携验证支路并行；汇总签发必须等待 Host 测试及全部验证成功。该支路仅复用 release profile 缓存，由 Cargo 核对源码，不拿 CI profile 二进制替代 release 产品。独立的手动 [Release Host benchmark](../../.github/workflows/release-host-benchmark.yml) 运行相同 Windows release 测试命令，固定本次工作流源码，不构建签发候选、不发布、不保存分支缓存；新增 runner 排队及缓存传输必须纳入墙钟比较。

固定旧版本的组装、Core 准备、解压与证明核验实验已退出日常 CI；其原始结果、来源和摘要保存在[历史实验归档](https://github.com/Starfie1d1272/Mizar/tree/archive/2026-10-17/evidence-index)。归档记录不能代替当前版本的资格验收，原固定候选过期后也不重建冒充原样本。
