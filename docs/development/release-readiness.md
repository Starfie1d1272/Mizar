# 版本与发布

本文维护 Mizar 的**长期发布约束与操作原则**；具体版本的进度、验收报告、变更列表和已发布资产分别由 GitHub Milestones、PR、[Releases](https://github.com/Starfie1d1272/Mizar/releases) 持有。当前发布实现以 [CI](../../.github/workflows/ci.yml)、[Release Qualification](../../.github/workflows/release-qualification.yml)、[Release Promotion](../../.github/workflows/release-promotion.yml) 和 [Box Sync](../../.github/workflows/box-sync.yml) 为准。

Box 文件上传默认使用 curl 和完整 multipart 请求体，分别限制建连、低速停滞及单次总耗时；正常传输可持续到总期限，停滞提前终止。每次上传最多 180 秒，上传和恢复读取总共最多 15 分钟、最多三次上传。日志记录 DNS、连接、TLS、发送字节、响应与退出码，保留 HTTPS 校验，不记录临时地址、凭据或服务器正文。传输失败后核对远端大小及 SHA-256，一致则继续；仅明确证明尚未发送请求体且目标缺失时有限重试，同名不同内容或结果不明则停止。更新指针替换不自动重发；完整回读与来源验证完成后才发布更新指针。恢复公开载体时，资格包附带的复用声明及证明必须逐字节相同才保留，同名不同内容保持终止。

Runtime 上传保留有限的文件级总时限；获取上传地址和每个分块的每次完整尝试各自受 180 秒限制。curl 明确证明某分块发送 0 字节时，仅在同一暂存目录对该分块有限重试并记录恢复时间；结果不明仍先核对完整暂存文件，绝不盲目重发分块。恢复重试不改写首次发行的 600 秒结果。

性能计时区分完整工作流、首次 runner 排队和重跑排队；重试及流程间等待仍计入端到端时间，不把最新尝试的启动时间当作首次排队。GitHub 最新 job 列表可能保留上一轮成功任务，其时间仍保留在证据中；本轮排队只从本轮启动后开始的 job 计算，没有此类任务时记为未知。内部资格汇总与晋级使用同步 ZIP 解压，之后仍完整核对 payload；便携及安装验收保留 Windows 资源管理器解压。解压性能对照必须使用固定原 ZIP 与来源证明，每次核对完整 payload；额外基准不能代替普通完整 CI 或新版本十分钟发行验收。

本文所称发行签名和证明指用于验证分发来源及产物身份的 GitHub provenance 等证明，不表示 Windows EXE 已经过 Authenticode 代码签名。

## 版本与兼容性

应用版本遵循 `MAJOR.MINOR.PATCH`；正式标签为 `v<应用版本>`，有风险的新能力可按需要使用 `-alpha.N`、`-beta.N`、`-rc.N` 预发布版本。不要为每次小修改单独发布一个 RC，也不能因为改动小就省略必要的验收。

发布基础设施接受纯稳定版本及 `alpha.N`、`beta.N`、`rc.N`，数字不带前导零，预发布序号 `N` 为正整数（从 `.1` 开始）。所有预发布沿用 main 的 Qualification / Promotion 门禁，精确标签、源码、二进制版本和原始签名必须一致；GitHub 标记为 prerelease 且 `latest=false`，不生成 Stable 更新清单、发布确认或索引，也不写入 Box Stable、Downloads、Updates 或 Archive。Box 自动与手动触发均显式报告预发布跳过，后续稳定版计时及其 artifact 上传一起跳过；不将缺失计时证据改判为成功。资源兼容性使用去掉预发布后缀的 Core 版本，授权仍绑定完整版本及原始资产。

预发布与稳定版均解压核验 Core，并通过隔离 SDK 验证 Full/Core 清单、ZIP、Setup 与资源包的来源证明；稳定版另验证更新清单和客户端 Core 选择。预发布只从对应 tag 人工下载完整 Setup 或 ZIP；稳定更新器仍只选择纯稳定版本，`channel: stable` 与 WebInstaller 的稳定限定不变。本轮不提供自动预发布渠道、独立应用身份或并存配置；安装版沿用现有安装和用户数据位置，升级、回退及数据兼容性须按目标版本验收，不承诺可与稳定版并存。脚本与 CI 检查不能替代 Windows / CS2 / OBS 实机证据。

| 变化  | 版本选择原则                                                               |
| ----- | -------------------------------------------------------------------------- |
| Patch | 与已有公开契约兼容的缺陷、安全或小型展示修正                               |
| Minor | 向后兼容的新能力、扩展和较明显的用户体验改进                               |
| Major | 公开契约出现不兼容变化，或产品进入需独立评审兼容性与迁移策略的重大版本阶段 |

路线图中的产品阶段是**演进目标**，并不自动决定技术改动的版本号。内部 HTTP/WS 协议、第三方 Provider、文件格式应按各自公开的兼容承诺版本化；不得以应用版本号代替协议兼容校验。

构建的应用版本须有单一权威来源，并与桌面配置、锁文件、发布标签和产物元数据一致；当前以 `apps/desktop/src-tauri/Cargo.toml` 的 `package.version` 为权威，通过现有版本检查验证其他副本。

## 正式发布不变量

1. **确定唯一构建身份**：可晋级候选只从 main 的资格工作流创建；输入精确 SHA、checkout、工作流上下文和签发前的产品 manifest 必须一致。晋级核对成功资格任务的 main 与精确源码，并通过 GitHub CLI 同时验证 main 签发工作流、来源 ref 和来源 SHA；客户端信任条件不放宽。冻结源码 SHA 和版本，所有验收、构建、安装器与公开文件均能追溯到这一身份；修复后重新评估受影响的验证范围。
2. **先验证再晋级**：候选应通过当前必要 CI、契约/回归验证和 Release Qualification；正式发布只晋级已经核验过的资产，不在晋级时重新编译另一份“看似相同”的程序。
3. **按风险做实测**：CS2、OBS、Windows 宿主、GSI/CSTV、安装和更新的变更须在相关真实环境验收。普通文档变更不需要重跑整场比赛；浏览器模拟也不能冒充原生性能、OBS 捕获或安装验证。
4. **安装与回滚可信**：验证升级、卸载、运行中阻断、带空格路径和用户数据保留。新版失败不能无提示销毁旧数据；任何不可逆迁移必须在发布前说明与验证。
5. **保留供应链证据**：记录源 SHA、产物身份、依赖/许可、SHA-256、资格构建与完整性验证。签名/证明的存在与验证结果须以当次发布事实为准，不能仅凭下载页写有散列值就宣称来源已认证。
6. **明确上线后的状态**：版本、变更、兼容性/迁移事项、已知限制与下载入口记录在本次 Release Notes。历史发布说明不因下一次发布而改写。

Windows 安装版与便携版属于不同的分发形态，用户数据路径和升级/回退语义也可能不同；当前操作步骤以[快速开始](../guide/quick-start.md)为准。交付名、发行清单和内容摘要遵循现有 qualification / promotion 脚本，不在这里复制一份易失效的构建参数列表。

| 场景               | 实机判定与证据                                                                                             |
| ------------------ | ---------------------------------------------------------------------------------------------------------- |
| 首次准备／旧版升级 | 标准启动可用；MulNX 版本支持启动器消息总线接口，旧版有准确的更新指引；取消和失败无本次进程残留             |

| 暂停／断流／换场   | 清空旧提示，恢复后重新对齐；开关与进程状态一致，失败原因和重试可用；记录重校准空窗                         |

## 发布过程

从 main 手动触发 Release Qualification，指定与应用版本一致的标签、资源参数和 `standard` 或 `hotfix` 类型。两种类型使用同一条发行路径：应用只编译一次，生成可下载的 Full、Core 与资源；同一次构建生成 Full、Core、安装器和启动元数据。两种类型都保留 `--app-version` 版本、摘要及来源证明校验；该命令不验证应用实际启动，不因 hotfix 更换旧客户端契约。Qualification 成功后自动晋级为 GitHub Release，Box 再独立异步同步；触发此流程会公开发行。两个签名工作流保留原名称，以兼容已发布客户端的信任策略。流程不再自动执行安装与产品验收；交互、升级、卸载和恢复是否可用须以实际使用为准。

600 秒是从资格触发至 Box 核验完成的性能目标，计时记录实际耗时、首次结果和恢复状态；另记 GitHub Release 首次公开的时间，该时间不代表后续授权上传或 Box 已完成。超时、重试或计时证据缺失不会被记作首次达标，也不会仅因超出目标阻断签名或 GitHub Release。签名、身份、完整性和实际传输失败仍须失败。各作业和网络操作保留有限超时，Box 失败不撤销已公开的 GitHub Release。Box 首次同步失败后，可手动触发 Box Sync 并填写原版本标签重试；补传单独计时，不重新构建或创建标签，仍复核既有发行资产与镜像字节。

发布流程失败时不得通过跳过真实门禁或改写正式标签掩盖问题；先修复根因，再生成新的可追溯候选。遇到功能性/安全性问题时，可发独立 Patch，不等待其它版本主题完工。

需要恢复时可手动运行 Promotion 并设置 `recovery=true`，复用已成功资格任务的原资产和证明；核验原 main 资格、来源、签名和资产，不要求等待性能目标到期。计时记录标记恢复，不计为首次发行达标。

草稿尚未生成标签时，已成功资格的显式恢复可传入草稿 Release ID，仅将完整核验过的六项公开资产暂存到同一草稿。按资格版本与源码核对草稿身份，拒绝已有标签、未知附件和同名异内容；已有或新上传附件必须完整回读并校验摘要。暂存不发布草稿、不创建标签、不触发 Box；制作人员完成发布后再按原资格执行恢复晋级并生成更新授权。

晋级单次 GitHub 读写最多 180 秒；新草稿的独立资产上传和完整回读每批最多三个并行；上传前先核对全部已有资产，失败时等待同批操作结束，不启动后续批次或自动重放结果不明的请求。晋级重试先核对标签及来源，逐个验证已存在资产的元数据和实际原字节，然后只补缺失资产；不覆盖同名不同字节。草稿或已公开但尚缺索引的 Release 可继续补齐。资源签发后的原字节暂存于本次晋级 CI artifact；资源证明已部分公开时必须从原记录恢复完整授权，不能重签混配。全部运行时资产验证通过后生成发布确认并上传单个 v2 更新索引，再验证原双签名。验收记录留在 CI artifacts。

独立官方资源同样消费冻结候选，不触发第二次 Core 编译。资格阶段构建真实 Pack，并将 `resource-descriptor.json` 绑定到 Core 版本、精确源码、原 ZIP 摘要、资源兼容范围、序号、有效期和固定下载地址；资格 main 工作流在同一证明中覆盖新资源描述符与 Pack；复用旧 Pack 时保留旧证明，仅证明当前描述符。操作者必须显式提供独立资源版本和递增序号，资源内容或源码身份变化时使用新的资源版本。

晋级在本次 main 精确源码的独立工具 worktree 中构造 `resource-publication.json` 与 `resource-catalog.json`，绑定原资格描述符摘要和实际晋级源码，并由既有晋级工作流签发证明。资格源码与晋级源码可以不同；原 Core、Pack 和资格证明保持原始字节。公开资产包含 Pack、描述符、目录、发行声明，以及描述符／Pack 的资格证明和目录／声明的晋级证明，共八份。客户端必须先从可信 Core 身份约束资格描述符，再验证 main 晋级目录的真实证明，之后才能使用目录策略和共享双证明验证器；镜像自报的目录、SHA 或 `trusted` 字段没有授权效力。

带资源接线的资格源码必须提供原资源 artifact，缺少资源、证明或兼容内容直接失败。历史资格源码没有接线时继续消费原历史候选，不补签或重发旧资产。已有 Release 的重试读取并验证原目录、声明、全部证明和公开资产身份，拒绝覆盖、重新签发已公开授权或降级；公开后逐项核对八份资产的唯一名称、大小、摘要与固定地址，通过后才进入 Stable 发布确认。Core-only 开发产物仍不可晋级；正式拆分分发必须由 Core 消费者实际集成可信目录与 Resource Store，并通过真实安装、恢复及离线验收。

发布身份入口串行执行 gh provenance 验证，避免并发初始化默认 TUF 缓存。Promotion 将产品复制到私有冻结目录，按原 bundle 字节 SHA-256、工作流及精确源码分组，每组由 gh 验证一个代表文件，再从认证的 DSSE 对每个必需名称和冻结文件 SHA-256 做唯一性校验；不同 bundle、来源或工作流不可合组。后续发布使用同一冻结文件，校验期间 bundle 或文件变化立即失败。gh 继续绑定固定 main signer、source-ref、精确源码和原 bundle，保留证书、透明日志及信任根验证；初始化失败保留脱敏原因。资源归档与声明保持其原证明和独立来源约束，不以旧阶段结果替代新快照或不同角色的授权。

## 分发、镜像与应用内更新

GitHub Releases 是完整正式资产、版本历史和溯源信息的公开入口；完整 Setup 与离线 ZIP 保留在 GitHub。Box 仅镜像轻量安装器、Core 安装后端、独立资源和必要机器元数据，必须与通过资格验收的原始资产字节一致。用户入口见[快速开始](../guide/quick-start.md)。`sync` 可对已经发布的同一版本执行精简迁移，不创建新 Release、不重签已发布元数据；`verify-downloads` 只读核验匿名目录和轻量安装器的完整原字节。精简迁移与验收共用固定公开 Downloads 目录读取器，不向公开入口发送资料库凭据；读取结果核对分享目录、文件路径、唯一名称和大小，归档仍逐项验证原发行身份及受控完整回读，公开目录响应不能授权写入。公开目录中的历史完整包先按其原始 Release 身份核验，再移入 Archive，已存在的归档必须内容一致；未知文件、更新版本或同名异内容直接阻断，不能清空目录。`/Stable/Music` 目录作为独立音乐资源保留，不进入、移动或删除，其中内容不参与应用发行身份判断；同名普通文件、Downloads 内同名目录及其他未知内容仍拒绝。旧书签仍打开 Stable，用户进入 Downloads 获取轻量安装器。历史 Offline 与 Archive 保留，不再提供将完整包恢复为日常镜像的兼容模式。

如果产品提供应用内更新，必须先验证更新元数据与来源身份，再核验安装包；**从同一不受信任来源同时获取文件和 SHA-256 并不足以证明发布者身份**。更新应明确区分安装版与便携版，正常退出后安装，不得在 Live 播出时擅自终止程序；网络、校验、安装或恢复失败时保持已安装版本可用。

轻量安装器首屏展示安装位置，首次安装可更改为安全的空目录；已登记安装沿用原位置，升级不迁移目录。完成页提供打开安装位置。新安装的 pending 恢复绑定同一安装器与原选定目录；更新准备记录与日志都证明未启动写入时可重开，启动歧义或活跃写入保留现场。恢复时先分别核验备份和当前目录；若当前目录已是完整旧版本，不再复制另一份完整恢复目录。恢复保留被换出的失败目录；错误诊断记录原始原因链和阶段，经脱敏后可复制、导出。

Stable 资格构建从原分发清单生成并证明 `update-manifest.json`，晋级核对精确源码和元数据后上传原资产。正式 Release 实际公开且完整原资产核对通过后，main 的晋级工作流生成并签发 `update-publication.json`，与原更新清单、两份原证明一起装入 `update-index.json`；资格签名不承担正式发布授权。冻结正式版本时同步 `scripts/qualification/update-release.json` 的版本和兼容范围，并完成 [CHANGELOG](../../CHANGELOG.md) 对应版本的正文；预发布版本不提供 Stable 更新清单或正式发布确认。来源身份分别绑定 main 的资格和晋级工作流，签名根由 Sigstore TUF 管理。没有更新清单的历史版本继续通过正式发布页下载；首个支持应用内更新的正式版本仍须手动升级后才能使用该能力。详细流程见[更新契约](../reference/updates.md)。

所有写入与归档完成后，发布指针前的独立完整 SHA256 回读每批最多三个并行，记录该阶段耗时；任一失败须等待同批在途读取结束，不启动下一批、不提交 latest。校验次数、大小和摘要判定不变，不复用写入前的哈希或以匿名 Range 代替完整回读。

Box 独立的 Runtime、Resources 与轻量入口传输可并行，任一路失败须先等待其余写入结束，不发布更新指针。完整 Setup 和离线 ZIP 不进入常规下载、上传或发布前回读清单；只在首次迁移公开目录中已有完整包时核验其原字节并归档。原素材未变时，从原版本技术目录校验并服务端复制同一 ZIP，保留旧客户端路径，复制后和发布指针前仍完整回读；不改原始素材来源。复制接口返回 405/501 时，先重新列出目标，存在的目标必须完整核验，仅目标缺失才上传已验证原 ZIP；404 无法证明接口不支持，响应不明时同样停止，并在同版重试时校验已落盘内容。

Box Sync 在同一 runner 完成发行与签名元数据准备，再以独立子进程并行运行 Runtime／Resources／Downloads 三条通道；各通道分别下载、验来源、上传及完整回读。通道各自使用独立文件和恢复状态，失败时等待全部在途通道结束，不推进最终阶段。 收到取消信号时停止各通道进程组并等待终止；已发送的远端写入结果仍可能未知，恢复时必须核对远端。保留的计划、脱敏通道状态与已有回执仅供诊断，不作为恢复成功凭据；强制终止可能无法保存证据。准备阶段只传递小型原始元数据和身份计划，回执绑定计划摘要、运行与尝试编号、资产名称、大小和 SHA-256，不携带令牌或临时地址。最终阶段仅在三条通道成功后校验回执、重新回读远端字节及匿名入口，再发布并完整回读索引；失败重跑时先核对已存在的原字节。

Runtime 阶段直接以传输完成后对目标的完整回读记录本次资产验证，元数据和 Core 均成功后生成回执；暂存和落位校验仍按原顺序执行。最终阶段仍独立完整回读全部资产，优先在首批读取 Core；任一失败等待同批读取结束，停止后续批次和索引发布。

Box 小型 JSON API 使用原生 HTTPS，限制建连及包含正文读取的总耗时，响应最大 2 MiB。只读 GET/HEAD 遇允许的暂态错误最多尝试三次，采用指数退避与随机抖动，遵守 Retry-After 的秒数或日期；等待超出恢复预算则停止。读取重试耗尽后停止当前同步，不再以整轮重试放大请求次数；必须先等待所有并发操作结束，任何结果不明的写入阻断继续。非成功响应及时释放正文并保留状态和 Retry-After，权限拒绝、未知错误、超限及无效 JSON 保持终止；目录创建、移动、复制等写入仅在 TLS 建连前失败、能确认请求尚未发送时自动重试，不盲目重放结果不明的写入。上传、资源复制和归档移动结果不明时，短间隔核对远端至多 90 秒；目标必须完整字节核验通过，移动还须确认原位置消失，才能继续。仅明确证明请求体未发送且目标缺失时可有限补传，结果不明或内容不符时保留现场。下载与原签名验证保持既有路径。

## 更新日志与发布正文

[CHANGELOG](../../CHANGELOG.md) 是用户变更与版本特定升级说明的唯一来源。各版本按新到旧排列，标题使用 `## [1.1.0]` 等精确版本号，可用 `## [Unreleased]` 暂存未冻结变更；发布时必须存在唯一、非空的精确版本正文。保留历史变更，已发布原文与资产继续由 GitHub Release 和 Git 历史追溯，不再维护单独的版本文档。

正文只使用 `###` 分组标题、段落、无序列表（最多两层缩进）或顶层有序列表；行内支持加粗、斜体、单反引号代码与 HTTPS 链接。不使用图片、HTML、表格、引用或代码块。`scripts/qualification/release-notes.mjs` 负责唯一提取与转换：GitHub 保留正文 Markdown，固定追加版本下载链接、使用手册、发行文件与构建校验信息；应用内使用标题和段落保留、无序列表转为 `•`、行内标记去除、链接只保留文字的纯文本。未支持格式明确报错，不在客户端另写转换或渲染逻辑。

版本、源码和资格任务链接由实际构建身份自动填入，固定发布者签名说明随分发政策变化维护。更新清单在资格构建时包含转换后的纯文本并签发来源证明；正文变更必须重新资格构建，不能在晋级时替换已签清单。生成 GitHub 正文供审阅可运行 `node scripts/qualification/release-notes.mjs <版本> <精确源码SHA> <资格任务ID> <输出文件>`；生成文件不代表已经发布。

镜像上传凭据只用于发布工作流，不进入客户端、公开文档或可下载产物。正式版本号、签名状态、自动更新能力与安装说明以对应 Release 和当前用户手册为准，不在本长期规范中维护每次发布的临时状态。
Box 的 Stable/Downloads 是用户入口，只保留最新轻量 WebInstaller；Runtime 存放 Core 更新后端与原机器元数据，Resources 存放独立资源，Archive 保留历史分发文件，Updates 存放原签名更新信封。分享入口保持 `?p=/Downloads`。必须完成原字节校验、历史归档与匿名轻量下载验收后，最后发布 Updates 最新清单。客户端只读凭据与发布上传凭据分开管理。

## 发行消费者与运行时依赖

| 消费者         | 实际需要                                                                                | 保存位置                                          |
| -------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------- |
| 用户           | 推荐轻量安装器 EXE；同一已验证 Core 与资源组成的完整离线 ZIP                            | 轻量安装器：GitHub / Box；完整离线 ZIP：仅 GitHub |
| 安装和更新程序 | Core 后端、原版本/分发清单与许可证、原 v2 双签名更新索引、资源归档及其原始目录/签名材料 | 同版本机器运输载体；Box 的 Runtime 技术目录       |
| 维护者         | 截图、测试报告、资格/晋升记录、安装器构建报告                                           | CI artifacts 与 CI 运行链接                       |

机器运输载体只聚合程序必须读取的原始字节，不建立新信任根，不装验收报告，也不创建永久技术 Release。资源 ZIP 单独运输。载体和所有读取端检查大小、白名单路径、重复条目、规范编码，解出的原字节仍由原签名验证。分散元数据附件不是常态发行目标。

旧更新器不再作为国内镜像的兼容目标；后续新构建的签名更新范围从已发布的 1.6.0 起，旧版用户保存资料并正常退出后手动安装当前轻量安装器。已发布 Release、标签、签名元数据与原始文件保持不变，不追改历史兼容声明。完整 Setup 仍在 GitHub 作为原始发行资产保留；移除 Box 的重复后端不改变 Core 选择、原始证明及安装恢复门禁。

推荐安装器只安装不含可选 EPL 媒体的正式 Core，然后通过唯一 Resource Store 获取首次资源缓存。同次 Qualification 先完整核验 Full，再分离并重新完整核验 Core 的独立身份；各自签名，不改原 Full/已签 Core。过渡离线 ZIP 保留原 Full 的已验证离线行为，旧客户端升级保留原 Full NSIS；不要求首次启动新增 TUF 验证。真正同 Core 离线组合仍需独立资格验收。开发 core-only 与 readiness 不能通过改标志代替实际证据。

现有 SDK 的历史缓存 receipt 从固定 Sigstore seed 核验原签名，允许已经安装的资源在 TUF 元数据过期后继续使用；这不等于允许冷机器首次安装。首次离线验证的前置接口补充原始 timestamp、snapshot，并检查 root 授权、角色版本/摘要绑定及各角色有效期，沿用同一 SDK 信任根。该接口不提供永久离线首次安装资格，尚未启用到发行或 Store 安装路径。

长期离线 ZIP 的关键依赖是明确首次安装的信任合同：若沿用在线 SDK 的 TUF freshness 要求，过期离线包必须更新；若要求长期冷机器断网首次安装，则需要在现有信任体系内单独审定可授权该行为的合同，不能把新安装改称缓存恢复。旧版本只读 Box 验证、真实旧签名的断网前置验证与 UI fixtures 均不冒充新产品安装验收。readiness 必须以真实产品资格与安装证据为准。

Promotion 对同次已成功资格任务的产品和验收证据并行下载到独立目录，两者全部完成后才校验来源与证据；任一失败阻断后续。同源产品、当前资源描述符和新资源归档在资格阶段一次签发，既有产品和资源证明文件仍分别保存该原 bundle；复用旧资源时不重签旧归档。产品复用原始 `qualification-provenance.json` 按原始 bundle 分组核验，更新证明与其字节相同时同组、历史不同证明分组，仍绑定 main 签发工作流、精确源码 SHA 和每个资产字节；缺失或无效 bundle 直接失败，不回退到放宽校验。证明核验的性能对照应固定原资产与证明，记录失败及包含准备时间的总墙钟；测量不替代全流程十分钟验收。

正式发行从 release profile 构建产品，CI 的 Windows 宿主构建使用独立的 ci profile。

固定旧版本的组装、Core 准备、解压与证明核验实验已退出日常 CI；其原始结果、来源和摘要保存在[历史实验归档](https://github.com/Starfie1d1272/Mizar/tree/archive/2026-10-17/evidence-index)。归档记录不能代替当前版本的资格验收，原固定候选过期后也不重建冒充原样本。

Box Sync 自动和手动同步默认使用 `transport=curl`；`native` 仅作为显式诊断备选，具有独立建连和空闲截止。curl 临时上传地址仅通过标准输入传递，不进入命令参数或日志，不跟随重定向。GitHub Release 资产单次下载（包括正文读取）最多 180 秒。Box 单次下载回读最多 180 秒，连续 60 秒无响应或数据时提前中止，并按既有只读规则重试；匿名入口单次下载也最多 180 秒。两种上传传输共享回执校验、远端原字节核对和最后发布更新指针的顺序；具体超时与次数以同步脚本为准。

Box Sync 的 `probe` 使用唯一临时文件顺序发送两块，再完整回读验证和清理，用于确认当前服务的分块上传支持；探测不会改动正式发行文件或更新指针。

Core 后端以 4 MiB 顺序分块写入唯一暂存目录，每块单次请求（包括响应读取）最多 180 秒，整次分块上传另有 900 秒聚合上限；完整原字节回读通过后才移动到 Runtime。结果不明时核对暂存文件，未落盘则使用新目录有限重试，保留异常现场，不重发单独末块。
